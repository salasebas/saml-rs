# Metadata trust and replay

Callers select metadata trust and replay storage independently of validation.
The defaults for both roles are recorded in [validation presets](https://samlrs.vercel.app/explanation/validation-presets/).

Metadata trust is `MetadataTrustPolicy`, passed to
`IdpDescriptor::from_metadata_xml` and
`SpDescriptor::from_metadata_xml`. Replay is `ReplayPolicy`, passed to
`SamlValidationContext::new`. Neither value is a field of
`SpValidationPolicy` or `IdpValidationPolicy`. The Web Browser SSO and Single
Logout field combinations do not select signed metadata, invent trust anchors,
or store replay.

Normative text is SAML Metadata 2.0 and Profiles 2.0, as corrected by Approved
Errata 05, plus Core 2.0 where a condition is named. Schema citations are the
OASIS metadata schema.

## Metadata trust

Typed import accepts a document the caller already holds. It does not publish
metadata, resolve a well-known location, query DNS, refresh a cache, or follow
TLS server authentication. Metadata §4 describes those mechanisms and says
other out-of-band mechanisms are permitted. Rules that obligate only that
resolution path stay outside this import.

| Rule | Actor | Direction | Level |
| --- | --- | --- | --- |
| Count entity members of a metadata group | Metadata consumer | Import an aggregate | Metadata §2.3.1 and the [metadata schema](https://docs.oasis-open.org/security/saml/v2.0/saml-schema-metadata-2.0.xsd) define members as direct `md:EntityDescriptor` children and members of direct `md:EntitiesDescriptor` groups. Extension content contributes no members. Requiring exactly one member is library policy because the import returns a single entity. |
| `ds:Signature` on `EntityDescriptor` or `EntitiesDescriptor` | Metadata publisher | Generate metadata | Optional. The schema marks the element optional. Metadata §3 says a signature is not always required when the relying party obtains the document directly over an authenticated secure channel. With `Credentials::with_metadata_signing_credential`, `SpConfigBuilder::build` and `IdpConfigBuilder::build` sign the metadata they generate, and `metadata_xml()` returns it signed. `metadata::sign_metadata` signs an `EntityDescriptor` or `EntitiesDescriptor` the application holds. The builders sign with the `AlgorithmPolicy::signature` algorithm. The digest is the one that algorithm names, and the signature's `KeyInfo` carries the signing certificate, which Metadata §3.1.5 allows |
| Sign at least the root element when that channel is absent | Metadata publisher | Generate metadata | Recommendation. Metadata §3. §4.3.3.2 also says published metadata documents should be signed. This import does not reject unsigned metadata because of that publisher recommendation. The caller selects `AllowUnsigned` when it has authenticated the document through another channel. Under that policy even a present signature is unverified |

Signatures from a peer are verified, and messages to it encrypted, with its role's certificates. A message signed with a key that only the peer's other role publishes is rejected. No OASIS receiver rule names that case, so the rejection is library policy. `Metadata::parse` has no role and reads every SSO role descriptor |
| A role's name identifier formats are the `NameIDFormat` elements of that role | Metadata consumer | Inbound | Metadata §2.4.2 and its schema type `NameIDFormat` as `xs:anyURI`. Generated messages use the normalized formats when the list is not empty. Generation choices are in [Web Browser SSO generation](web-browser-sso-generation.md). No input is rejected. Generic `Metadata::parse` reads every SSO role descriptor |
| An endpoint's `Binding`, `Location`, `ResponseLocation`, `index`, and `isDefault` are read with XML Schema whitespace collapse | Metadata consumer | Inbound | Schema reading. Metadata §2.2.2 types `Binding`, `Location`, and `ResponseLocation` of `EndpointType` as unqualified `anyURI` attributes, and §2.2.3 types `index` of `IndexedEndpointType` as `unsignedShort` and `isDefault` as `boolean`. XML Schema Part 2 §4.3.6 collapses the whitespace of these datatypes (§§3.2.17, 3.3.23, and 3.2.2). `IdpMetadata` and `SpMetadata` collapse space, tab, carriage return, and line feed on every `SingleSignOnService`, `ArtifactResolutionService`, `SingleLogoutService`, `ManageNameIDService`, and `AssertionConsumerService` of the role read, and `Metadata::parse` on every `SingleLogoutService`, before a binding is matched or a location is returned or compared. A namespace-qualified attribute with one of these local names is a foreign attribute and is not read. A value that is only whitespace is read as empty, and the empty-value handling of each endpoint applies. Library policy: `IdpMetadata::artifact_resolution_services` returns `SamlError::Invalid` for an `ArtifactResolutionService` whose `Binding`, `Location`, or `index` is empty or only whitespace, or that has only a namespace-qualified one. Metadata §§2.2.2 and 2.2.3 mark these attributes required, but the schema allows an empty `anyURI`, and Core §1.3.2 binds the writer of a URI reference, not the reader. The rejection of an empty or missing attribute predates the whitespace collapse. A value that is only whitespace is the same `anyURI` as an empty one after the collapse, so it gets the same answer |
| A peer's role is the role descriptor of that kind that lists SAML 2.0 | Metadata consumer | Inbound | Library policy. Metadata §2.4.1 makes `protocolSupportEnumeration` a required whitespace-delimited set of URIs naming the protocols a role supports, and says that for SAML V2.0 entities it must include `urn:oasis:names:tc:SAML:2.0:protocol`. That rule obligates the metadata publisher. Metadata §2.3.2 recommends that role descriptors of one type not share a `protocolSupportEnumeration` value, and leaves selection among those that do undefined. No clause, and no Approved Errata 05 change, requires a SAML 2.0 relying party to ignore a role that does not list that URI. `IdpDescriptor` and `IdpMetadata` read keys, `WantAuthnRequestsSigned`, `NameIDFormat`, endpoints, and `validUntil` only from the `IDPSSODescriptor` elements in the SAML metadata namespace whose `protocolSupportEnumeration` lists that URI. `SpDescriptor` and `SpMetadata` read `SPSSODescriptor` the same way. A role that lists only another protocol, such as SAML 1.1, is ignored wherever it appears in the entity. An entity with no such role is refused with `SamlError::MissingMetadata` naming the element. Several such roles are read together, except the default `AssertionConsumerService`, which comes from the first, because Errata 05 E37 makes a default the first `isDefault` endpoint within a role. The restriction keeps a role the peer publishes for another protocol from supplying keys, flags, or endpoints for SAML 2.0 messages. `Metadata::parse` has no role and reads every SSO role descriptor |
| `KeyDescriptor` `use` names the key's purpose | Metadata consumer | Inbound | Mandatory reading of the published purpose. Errata 05 E62 says `signing` covers signing, `encryption` covers wrapping encryption keys, and an omitted `use` covers both. Signature verification uses the certificates of `KeyDescriptor`s with `use="signing"` or no `use`. Encryption uses those with `use="encryption"` or no `use`. A key published for one use is never used for the other. Errata 05 E68 says a relying party should allow any key that several `KeyDescriptor`s publish for the same use, so every such certificate is tried when verifying |
| Several `KeyDescriptor use="signing"` on this entity's role | SP and IdP metadata publisher | Generate metadata | Optional. Metadata §2.4.1 and the metadata schema's `RoleDescriptorType` allow several `KeyDescriptor` elements. Errata 05 E68 amends §2.4.1.1 so any included key may be used and recommends that relying parties accept any of them. `Credentials::with_additional_signing_certificate` publishes each certificate in its own signing descriptor after the signing certificate, in the order added. Signing still uses only the signing key and signing certificate. No receiver rule changes |
| Several `KeyDescriptor use="encryption"` on this entity's role, and decryption with any of them | Metadata publisher, and the relying party that decrypts | Generate metadata, inbound decryption | Optional for the publisher, recommendation for the relying party. Metadata §2.4.1 allows several `KeyDescriptor` elements. Errata 05 E68 amends §2.4.1.1: several `KeyDescriptor`s with the same `use`, or none, mean any of the included keys may be used by the containing role, and a relying party should allow any of them. `Credentials::with_decryption_credential` publishes the certificate of each decryption credential in its own `KeyDescriptor`, in the order added. Decrypting `EncryptedAssertion`, `EncryptedID`, `EncryptedAttribute`, a `LogoutRequest` `EncryptedID`, a requested `AuthnRequest` subject `EncryptedID`, and a `ManageNameIDRequest` `EncryptedID` or `NewEncryptedID` tries the decryption keys in the same order and keeps the first that decrypts. The RSA-v1.5 key-transport refusal applies before any key is tried. When no key decrypts, the error is the one the first key returns |
| The certificate of each signing and decryption credential holds the public key of its private key | SP and IdP metadata publisher | Generate metadata | Library policy. Metadata §2.4.1.1 says `KeyDescriptor` describes the keys an entity uses to sign data or receive encrypted keys, and no OASIS text tells the publisher to check them. With a crypto provider, `SpConfigBuilder::build` and `IdpConfigBuilder::build` load each key and certificate of `Credentials`, including each additional signing certificate. They return `SamlError::Crypto` when one does not load, when a key field holds only a public key, or when a key does not match its certificate. A peer verifies this entity's signatures and encrypts for it with the published certificates, so a mismatched pair would fail every exchange with that peer |
| `entityID` is unique across every entity that interacts in one deployment | Metadata publisher | A deployment | Mandatory. Metadata §2.2.1. The generator writes the caller-supplied identifier and does not police uniqueness across a deployment |
| Role descriptor children follow the schema sequence | Metadata publisher | Generate metadata | Mandatory. Metadata §§2.4.1–2.4.4 and the [OASIS metadata schema](https://docs.oasis-open.org/security/saml/v2.0/saml-schema-metadata-2.0.xsd) define the sequence through role type extension. The typed builders and standalone generators write `KeyDescriptor`, `ArtifactResolutionService` (IdP only), `SingleLogoutService`, `ManageNameIDService`, `NameIDFormat`, then `SingleSignOnService` (IdP) or `AssertionConsumerService` (SP). Each endpoint group preserves the configured order, including repeated endpoints. |
| Entity-level `Organization`, then `ContactPerson`, follow the role descriptors | Metadata publisher | Generate SP and IdP metadata | Optional elements with mandatory ordering when present. Metadata §2.3.2 and `EntityDescriptorType` in the [OASIS metadata schema](https://docs.oasis-open.org/security/saml/v2.0/saml-schema-metadata-2.0.xsd). Typed and raw configs expose `organization` and `contacts`; builders expose `organization`, repeatable `contact`, and `contacts`. Both generators write them after the role descriptor when configured. |
| An organization has one or more names, display names, and URLs, each with `xml:lang` | Metadata publisher | Generate metadata with `Organization` | Mandatory when present. Metadata §§2.2.4, 2.2.5, and 2.3.2.1 and the metadata schema. Generation rejects an empty list, a language tag outside the [XML Schema 1.0 §3.3.3](https://www.w3.org/TR/xmlschema-2/#language) lexical pattern, or XML-forbidden text with `SamlError::Invalid`. Organization URLs and role `errorURL` values must be absolute URI references under Core §1.3.2. This does not validate language tags against a registry |
| A contact has one enumerated `contactType` and zero or more `mailto:` email URIs | Metadata publisher | Generate metadata with `ContactPerson` | Mandatory when present. Metadata §2.3.2.2 defines the five contact types, optional company and names, and repeatable email and telephone elements. `ContactType` represents the five values plus the security extension. Generation rejects a non-`mailto:` email URI with `SamlError::Invalid`; it does not test mailbox delivery |
| Publish the REFEDS security contact extension | Metadata publisher | Generate an explicitly configured security contact | Optional extension. `ContactType::Security` writes `contactType="other"` and `{http://refeds.org/metadata}contactType="http://refeds.org/metadata/contactType/security"` per the [REFEDS extension](https://wiki.refeds.org/spaces/STAN/pages/44957728/Security%2BContact%2BMetadata%2BExtension%2BSchema). This supports publishing the extension only. It does not assert Sirtfi compliance or require its additional contact details |
| Publish `errorURL` on the SSO role descriptor | Metadata publisher | Generate SP and IdP metadata | Optional under Metadata §2.4.1. Typed and raw `error_url` and the builder method write it only when configured. This does not claim the saml2int profile, which requires it for an IdP |
| Expose entity-level organization and contacts without changing imported XML | Metadata consumer | Read imported metadata | Informative data under Metadata §§2.3.2.1–2.3.2.2. Shared `Metadata::organization` and `contacts` return owned values through both raw metadata and typed descriptors. They read direct entity children and resolved namespaces, including inherited XML and REFEDS namespace bindings. Import adds no rejection for description content. The accessors return `SamlError::Invalid` for multiple organizations, missing `xml:lang`, or missing or unknown `contactType`, as applicable. They do not enforce outbound value validation on imported data |
| Each written `NameIDFormat` is an absolute URI reference | Metadata publisher | Generate metadata | Mandatory. Metadata §2.4.2 makes `NameIDFormat` an `anyURI` that names a name identifier format, with Core §8.3 values as examples. The metadata schema alone allows any `anyURI`. Core §1.3.2 requires a URI reference value in a SAML-defined element to have a non-whitespace character and to be absolute, as read in [identifiers](identifiers.md#name-identifier-formats). `generate_sp_metadata` and `generate_idp_metadata` return `SamlError::Invalid` for a written value that is not one, and so do `SpConfigBuilder::build` and `IdpConfigBuilder::build` for a configured `NameIdFormat`. Every configured value is written and checked. Service provider metadata without a configured format advertises `emailAddress` |
| Each written endpoint `Location` is an absolute URI reference | Metadata publisher | Generate metadata | Mandatory. Metadata §2.2.2 types `Location` as `anyURI` and leaves its syntax to the binding. Core §1.3.2 requires a URI reference value in a SAML-defined attribute to have a non-whitespace character and to be absolute. `generate_sp_metadata` and `generate_idp_metadata` return `SamlError::Invalid` for a `SingleSignOnService`, `ArtifactResolutionService`, `SingleLogoutService`, `ManageNameIDService`, or `AssertionConsumerService` `Location` that is not one. They do not require HTTP(S). Typed endpoints take `EndpointUrl`, which also requires an HTTP(S) URL. Metadata import does not reject a relative `Location` |
| An `IDPSSODescriptor` has a `SingleSignOnService` and an `SPSSODescriptor` an `AssertionConsumerService` | Metadata publisher | Generate metadata | Mandatory. The metadata schema declares each element in `IDPSSODescriptorType` and `SPSSODescriptorType` with the default `minOccurs` of 1, and Metadata §§2.4.3 and 2.4.4 list them as one or more. `generate_idp_metadata` and `generate_sp_metadata` return `SamlError::MissingMetadata` naming the element when the config has none, and so do `IdpConfigBuilder::build` and `SpConfigBuilder::build` |
| Each `AssertionConsumerService` `index` is unique within its `SPSSODescriptor` | Metadata publisher | Generate metadata | Mandatory. An endpoint without one is written with its position, or with the smallest unused index when another endpoint already has that position. Metadata import does not reject a duplicate. Looking up an index that several endpoints share returns `SamlError::Invalid` |
| Each `ArtifactResolutionService` `index` is unique within its `IDPSSODescriptor` | Metadata publisher | Generate metadata | Mandatory. Metadata §2.2.3 makes `index` a required unique `unsignedShort` among like elements in the same parent. `generate_idp_metadata` and `IdpConfigBuilder::build` return `SamlError::Invalid` when two endpoints share an index. On import, `IdpMetadata::artifact_resolution_services` returns `SamlError::Invalid` for a duplicate |
| `isDefault` appears only on an indexed endpoint | Metadata publisher | Generate metadata | Mandatory. The metadata schema declares `isDefault` on `IndexedEndpointType` only. `SingleSignOnService`, `SingleLogoutService`, and `ManageNameIDService` are `EndpointType`, and Metadata §2.2.2 requires any other attribute on them to be namespace-qualified. The generator writes `isDefault` on `AssertionConsumerService` only and ignores `Endpoint::is_default` on other endpoints |
| An enveloped signature on the signed root | Metadata publisher, when signing | Generate the signed element | Mandatory. Metadata §3.1.1. The signer writes one enveloped signature over the root. `RequireSignature` rejects a signature that is not enveloped. The same rule applies to a root `EntitiesDescriptor` and a root `EntityDescriptor` |
| The signature is the first child of the signed root | Metadata publisher, when signing | Generate the signed element | Mandatory. `EntityDescriptorType` and `EntitiesDescriptorType` in the metadata schema start with an optional `ds:Signature`, before `Extensions`, so a root holds at most one. The signer writes the signature as the first child, and `metadata::sign_metadata` returns `SamlError::Invalid` for a root that already has one |
| An identifier on the signed root, and one reference whose URI is `#` plus that identifier | Metadata publisher, when signing | Generate the signed element | Mandatory. Metadata §3.1.2. The signer keeps the root's `ID`, or writes a generated one when the root has none, and writes one reference to it. `metadata::sign_metadata` returns `SamlError::Invalid` for an `ID` that is not an XML NCName, the lexical space of the schema's `xs:ID`. `RequireSignature` rejects a signed root with no identifier and a signature that does not contain exactly that one reference. The signature must still cover the signed root |
| Exclusive canonicalization in `CanonicalizationMethod` and as a transform | Signer | Generate signed metadata | Recommendation. Metadata §3.1.3. The signer uses exclusive canonicalization without comments in both places, and no option selects another method |
| No transform other than enveloped signature or exclusive canonicalization, with or without comments | Signer and verifier | Generate signed metadata, inbound `RequireSignature` | Recommendation. Metadata §3.1.4. The signer writes only the enveloped-signature and exclusive canonicalization transforms. `RequireSignature` rejects other transforms. `RequireSignatureAllowingOtherCanonicalization` also accepts inclusive canonicalization, and still rejects a transform that can drop part of the signed element |
| No `ds:Object` in a metadata signature | Signer and verifier | Generate signed metadata, inbound `RequireSignature` | Recommendation. Approved Errata 05 E91 says `ds:Object` should not be present, and that verifiers should reject it because it can carry unsigned data. The signer writes none. All require-signature options reject it. There is no relaxation |
| No `ds:Object` in a message signature | Verifier of a message signature | Inbound | Recommendation. Core §5.4.5, added by Approved Errata 05 E91, says verifiers should reject a signature that contains `ds:Object` because it can carry unsigned data. Under `XmlSignatureProfile::ExcludeWeakAlgorithms`, the default profile, and `StrictRsaSha2`, a signature that authenticates the accepted `Response`, `Assertion`, `AuthnRequest`, `LogoutRequest`, or `LogoutResponse` and has a `ds:Object` child returns `SamlError::SignedReferenceMismatch`, on HTTP-POST and SOAP alike. `AllowWeakAlgorithms` relaxes it |
| No MD5 or RIPEMD-160 signature or digest algorithm, and no RSA signing key shorter than 2048 bits, on a metadata signature | Metadata consumer | Inbound `RequireSignature` | Library policy, on. No OASIS rule requires the rejection. Metadata §3.1.1, as replaced by Errata 05 E81, says any algorithm defined for use with XML Signature may be used, and Conformance §4.1 with E50 makes its list a minimal set. XML Signature 1.1 §6.2 says MD5 `SHOULD NOT` be used in `DigestMethod`, a rule on use, and §6.4.2 lets a verifier use an RSA key of 1024 bits or less. The rejection protects the trust root of the peer's keys: the certificates a verified document publishes are then trusted for its messages. `RequireSignature` and `RequireSignatureAllowingOtherCanonicalization` reject such an algorithm with `SamlError::AlgorithmUnsupported` on a build that verifies it, and do not verify with a pinned RSA certificate shorter than 2048 bits. `RequireSignatureAllowingWeakAlgorithms` relaxes it and keeps the transform rules of `RequireSignature`. The algorithms are listed in [weak algorithms and keys](xml-security-algorithms.md#weak-algorithms-and-keys) |
| When `RequireSignature` is selected, the signature covers the signed root | Metadata consumer | Inbound | Mandatory once that caller option is selected. Metadata §3.1.2 requires the signature to cover the signed element and its children. The import rejects a signature that does not cover the root |
| A root `EntityDescriptor` carries at least one of `validUntil` and `cacheDuration` | SP and IdP metadata publisher | Generate single-entity metadata | Mandatory. Metadata §2.3.2 requires a lifetime on the root. The `EntityDescriptorType` schema declares each attribute individually optional. `generate_sp_metadata`, `generate_idp_metadata`, and both config builders write the attributes selected by `MetadataLifetime`. A `validUntil` value is written in UTC and truncated to whole seconds. Without a configured lifetime, both roles write `cacheDuration="PT86400S"`. This producer rule adds no import rejection. Metadata §2.3.1 sets the same rule for root `EntitiesDescriptor` documents, which these APIs do not generate |
| Default to a one-day refresh interval | SP and IdP metadata publisher | Generate single-entity metadata with no configured lifetime | Library policy. Neither Metadata §2.3.2 nor Approved Errata 05 prescribes an interval. One day gives consumers a daily refresh target without assigning a fixed expiration to metadata generated once at config build. Approved Errata 05 E94 distinguishes cache staleness from expiration |
| Do not use metadata at or after `validUntil` | Metadata consumer | Use metadata | Mandatory when the attribute is present. Errata 05 E94 adds §4.3.2: metadata must be treated as invalid at that time, and invalid metadata must not be used. The effective expiration is adjusted downward by parent elements, and a nested value may only shorten the parent (E76). `IdpDescriptor` and `SpDescriptor` import keep the earliest `validUntil` of the enclosing `EntitiesDescriptor` elements, the `EntityDescriptor`, and the role descriptors that descriptor reads: `IDPSSODescriptor` or `SPSSODescriptor`. Every typed flow that uses the descriptor returns `SamlError::TimeWindowInvalid` with `TimeWindowField::MetadataValidUntil` at or after that instant. A flow that takes a `SamlValidationContext` compares with its clock; any other flow compares with the system clock. No clock skew applies. Another role descriptor of the entity does not bound this role. When the entity has several descriptors of this role, the earliest bounds all of them, because the descriptor reads them together; that is library policy. Import returns the same error for a value that is not an `xs:dateTime` with a timezone. Rejecting a schema-valid value without a timezone is library policy: XML Schema 1.0 §3.2.7.4 leaves its order against an instant indeterminate, so the expiry cannot be decided. Import interprets `24:00:00` as midnight on the next day in the supplied timezone, including when the seconds have an all-zero fraction ([XML Schema 1.0 §3.2.7.1](https://www.w3.org/TR/xmlschema-2/#dateTime)). The import accepts local years 0001–9999 before and after rollover. XML Schema 1.0 excludes year zero, and the library uses the four unsigned digits supported by `time`'s RFC 3339 parser for the remaining range. The same parser rejects leap seconds outside the last minute of a UTC month. These parser limits are library policy. The metadata schema declares `validUntil` unqualified. Only the unprefixed attribute supplies an expiry. `Metadata::parse` does not evaluate `validUntil` |
| Base caching on `cacheDuration` | Metadata consumer | Cache resolved metadata | Mandatory for a consumer that caches. Errata 05 E94 replaces §4.3.1: caching follows `cacheDuration`, and a stale copy may still be used. E76 lets a nested value only shorten the parent. Typed import does not cache metadata, so this is not a preset field. An elapsed `cacheDuration` does not make a descriptor unusable, because E94 distinguishes stale metadata from invalid metadata |

## Entity attributes

Normative text is the
[SAML V2.0 Metadata Extension for Entity Attributes](https://docs.oasis-open.org/security/saml/Post2.0/sstc-metadata-attr.html)
(MDAttr), Committee Specification 01. The rows for the four named attributes
also cite [RFC 8409](https://www.rfc-editor.org/rfc/rfc8409), the
[SAML V2.0 Identity Assurance Profiles](https://docs.oasis-open.org/security/saml/Post2.0/sstc-saml-assurance-profile.html),
and the [SAML V2.0 Subject Identifier Attributes Profile](https://docs.oasis-open.org/security/saml-subject-id-attr/v1.0/cs01/saml-subject-id-attr-v1.0-cs01.html).
These rows do not claim saml2int, and the library leaves attribute release by
category to the application.

| Rule | Actor | Direction | Level |
| --- | --- | --- | --- |
| `mdattr:EntityAttributes` in an `EntityDescriptor`'s `Extensions` binds its attributes to that entity. In an `EntitiesDescriptor`'s `Extensions`, it binds them to each `EntityDescriptor` in the group | Metadata consumer | Read imported metadata | Optional extension. MDAttr §2.2 lets consumers process or ignore it, and §2.3 states the binding. `Metadata::entity_attributes`, `SpDescriptor::entity_attributes`, and `IdpDescriptor::entity_attributes` return the `saml:Attribute` children of every `mdattr:EntityAttributes` in the `Extensions` of every enclosing `EntitiesDescriptor` and of the `EntityDescriptor`, outermost group first. They read the same document whose root `RequireSignature` verified. Import adds no rejection. An attribute without `Name` returns `SamlError::Invalid` from the accessor |
| `EntityAttributes` elsewhere has no defined meaning | Metadata consumer | Read imported metadata | MDAttr §2.3 leaves the meaning undefined anywhere other than those two `Extensions`. The accessors do not read `EntityAttributes` in a role descriptor's `Extensions` or in an element outside the metadata, `mdattr`, or assertion namespaces |
| A `saml:Assertion` in `EntityAttributes` is independently signed and holds one attribute statement about the entity | Metadata publisher | Generate metadata | Mandatory when present. MDAttr §2.4. The accessors do not read `saml:Assertion` children, and the generators do not write them |
| `EntityAttributes` appears at most once in one `Extensions`, and an `EntitiesDescriptor` carries no `saml:Assertion` in it | Metadata publisher | Generate metadata | Mandatory. MDAttr §2.3. The generators write one `EntityAttributes` with `saml:Attribute` children only. No receiver rule asks for rejection, so the accessors read every `EntityAttributes` they find |
| Publish entity attributes | SP and IdP metadata publisher | Generate metadata | Optional extension. MDAttr §2.3. `SpMetadataInput::entity_attributes`, `IdpMetadataInput::entity_attributes`, and the builders' `entity_attribute` and `entity_attributes` write one `Extensions` with one `mdattr:EntityAttributes` as the first child of `EntityDescriptor`, where `EntityDescriptorType` in the metadata schema places `Extensions`. Each value is written without `xsi:type`, and a `FriendlyName` is written when set and read back. Generation returns `SamlError::Invalid` for a `NameFormat` that is not an absolute URI reference, an `AttributeNameFormat::Basic` name that is not an XML name, or text XML cannot carry. saml2int SDP-SP39 places the element in the SP role's `Extensions`. Generation follows MDAttr §2.3 instead, which the Subject Identifier profile §3.5.1 cites, and which Shibboleth follows by reading only entity and group `Extensions` |
| A well-known entity attribute is the attribute with its `Name` and the URI `NameFormat` | Metadata consumer | Read imported metadata | Library reading. RFC 8409 §§3.1 and 4.1, Identity Assurance §3.3, and Subject Identifier §3.5.1 each name the URI `NameFormat`. `EntityAttributes` also matches an attribute with no `NameFormat` or the unspecified one, because Core §2.7.3.1 gives an absent `NameFormat` the unspecified meaning, and the Shibboleth `EntityAttributes` predicate matches such an attribute. Another `NameFormat` names a different attribute. `FriendlyName` plays no part, as Core §2.7.3.1 requires |
| Entity category and entity category support values are URIs, compared as opaque strings, and repeated attributes combine | Metadata consumer | Read imported metadata | RFC 8409 §§3.1–3.2 and 4.1–4.2. `EntityAttributes::entity_categories` and `entity_category_support` return the values of every matching attribute, in order, without normalization. A category on an enclosing `EntitiesDescriptor` is included because MDAttr §2.3 binds it to the entity. RFC 8409 defines the attribute only on `EntityDescriptor` |
| Assurance certification values are framework URIs, on the identity provider's `EntityDescriptor` or an enclosing `EntitiesDescriptor` | Metadata consumer | Read imported metadata | Identity Assurance §§3.2–3.5. Several values are allowed. `EntityAttributes::assurance_certifications` returns them in order, including REFEDS Sirtfi's `https://refeds.org/sirtfi` |
| A relying party that uses metadata publishes `subject-id:req` with exactly one value: `subject-id`, `pairwise-id`, `none`, or `any` | Relying party metadata publisher | Generate metadata | Mandatory when the deployment uses the profile. Subject Identifier §3.5.1, and §4.2 requires a relying party's metadata generator to support it. `Attribute::from(SubjectIdRequirement)` writes the name, the URI `NameFormat`, and one value without `xsi:type`. Generation does not add the attribute when the caller does not configure it |
| Read the subject identifier a relying party requires | Asserting party | Read imported metadata | Library policy. Subject Identifier §3.5.1 defines no asserting-party behaviour. `EntityAttributes::subject_id_requirement` returns `None` without the attribute. It returns `SamlError::Invalid` for an attribute without exactly one value, a value outside the four, or two attributes that require different identifiers, because the profile rules those out and one requirement cannot be chosen from them. Import itself does not reject them |

## Replay

For HTTP-POST SSO responses, the service provider requires a caller-owned
cache shared across requests. A deployment with several nodes needs atomic
duplicate detection across all nodes. Other bindings retain their own rules.

| Rule | Actor | Direction | Level |
| --- | --- | --- | --- |
| Bearer assertions delivered by HTTP POST are not replayed | Accepting service provider | Inbound `finish_sso` and `accept_unsolicited_sso` | Mandatory for HTTP POST. Profiles §4.1.4.5. Approved Errata 05 E26 replaces only the signing sentence at lines 600–601 and leaves this paragraph in place. After response parsing and verification, `ReplayPolicy::Disabled` returns `SamlError::ReplayCacheRequired`. With `RequireCache`, a duplicate or storage error prevents acceptance, including on the outstanding-logout variants |
| The kept HTTP POST identifier is the bearer assertion `ID`, for the `SubjectConfirmationData@NotOnOrAfter` window | Accepting service provider | Inbound | Mandatory for the HTTP POST rule above. Profiles §4.1.4.5 names that identifier and that window. The stored deadline is that attribute plus the context `NotOnOrAfter` skew. Profiles §4.1.4.3 checks bearer `NotOnOrAfter` subject to allowable clock skew, and Approved Errata 05 E92 is the guidance for that allowance. An earlier `Conditions` or `AuthnStatement` instant does not shorten the assertion identifier. With several bearer confirmations, the window is the latest bearer `NotOnOrAfter` that is a UTC instant, for the session assertion and every other direct assertion alike. Profiles §4.1.4.3, as replaced by Approved Errata 05 E26, needs only one bearer confirmation to satisfy the checks, and that one is a UTC instant. Another value, such as an offset form, is ignored for the deadline and does not fail replay storage. The time-bound row in [Web Browser SSO acceptance](web-browser-sso-acceptance.md) says which values are UTC instants. Choosing the latest value is library policy. It keeps the identifier at least as long as the confirmation that satisfied the checks |
| Also store the Response `ID` | Accepting service provider | Inbound | Library policy. It is stored only when the caller supplies a cache. Its deadline remains the earliest of `Conditions`, bearer `SubjectConfirmationData`, and every `AuthnStatement`, plus the same skew. That deadline can be earlier than the assertion identifier |
| Optional replay storage for HTTP-POST-SimpleSign responses | Accepting service provider | Inbound | Library policy. Profiles §4.1.4.5 states the replay duty for HTTP POST. Security considerations §7.1.1.4 defers replay countermeasures to the binding and does not add a second receiver requirement. Storage on HTTP-POST-SimpleSign happens only when the caller supplies a cache |
| `AuthnRequest` `ID` | Identity provider | Inbound `receive_sso` | Library policy. Web Browser SSO does not require the identity provider to remember request identifiers. `receive_sso` stores the ID only when the caller supplies a cache, and that path always requires `SamlValidationContext::with_replay_retention`. It does not read `NotOnOrAfter` |
| `LogoutRequest` `ID` | Logout recipient | Inbound `receive_slo` | Library policy. Single Logout does not require an identifier cache. Storage happens only when the caller supplies a cache. The deadline is `NotOnOrAfter` plus the context `NotOnOrAfter` skew when that attribute is present; otherwise the caller must set `with_replay_retention`. Rejecting an expired `LogoutRequest@NotOnOrAfter` remains the separate library policy already recorded for logout |
| `LogoutResponse` `ID` | Original requester | Inbound `finish_slo` | Library policy. Single Logout does not require an identifier cache. `finish_slo` stores the ID only when the caller supplies a cache, and that path always requires `with_replay_retention`. It does not read `NotOnOrAfter` |
| Do not retain an assertion that carries `<OneTimeUse>` | Relying party that would retain the assertion | Inbound | Mandatory when the element is present. Core §2.5.1.5 `MUST NOT` be retained for future use. For validity, the condition is always Valid. Typed SSO does not retain the assertion for later protocol use, so this is not a preset field and it is not part of the caller replay cache |
| Use a `<OneTimeUse>` assertion immediately | Relying party | Inbound | Recommendation. Core §2.5.1.5. It does not become a rejection of an assertion that arrives later |

## Typed metadata accessors

The peer descriptors expose HTTP(S) endpoints as `EndpointUrl` using the
binding type for SSO requests, SSO responses, or logout. Selection uses the
same role, indexed default, and `ResponseLocation` rules as the raw reader.
A selected non-HTTP(S) URL returns `SamlError::Invalid` from the accessor.
Import itself does not reject it. This is the library's typed endpoint
contract. Metadata §§2.2.2 and 2.2.3 use `anyURI` and do not impose HTTP(S).

Raw and typed artifact endpoint publishing both use `ArtifactResolutionService`,
which requires `EndpointUrl` and publishes SOAP. The HTTP(S) restriction is
library policy on publishers. The raw metadata reader continues to preserve
unknown artifact binding URIs and locations. Resolving an artifact still checks
that its selected endpoint uses SOAP.

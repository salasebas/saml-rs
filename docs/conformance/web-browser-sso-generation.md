# Web Browser SSO generation rules

Producer rules for typed Web Browser SSO generation: service-provider
`start_sso`, and identity-provider `respond_sso` and `initiate_sso`.
`SpValidationPolicy::default` leaves AuthnRequest signing and identifier
creation off. `IdpValidationPolicy::default` does not turn assertion
encryption on. Both config builders use these defaults.
See [validation presets](https://samlrs.vercel.app/explanation/validation-presets/).

Normative text is SAML Core 2.0, Profiles 2.0, and Bindings 2.0, as corrected
by Approved Errata 05. HTTP-POST-SimpleSign is the supported CD04 binding.
Schema citations are the OASIS assertion and protocol schemas. A profile or binding rule is used when it narrows Core for this flow.

A response delivered as an HTTP-Artifact is built by these same rules. Its
delivery is in [HTTP-Artifact response](web-browser-sso-artifact.md).
The PAOS response producer follows the same assertion rules for ECP
(Profiles §4.2.3.6).

## Service provider AuthnRequest

| Rule | Actor | Direction | Level |
| --- | --- | --- | --- |
| `Issuer` is present, is the service provider's identifier, and omits `Format` or sets it to `entity` | Service provider | Generate AuthnRequest | Mandatory. Profiles §4.1.4.1 |
| `ID`, `Version` `2.0`, and UTC `IssueInstant` are present | Service provider | Generate AuthnRequest | Mandatory. Protocol schema `RequestAbstractType`; Core §1.3.3 |
| Do not generate a leap-second time | Service provider | Generate any instant | Mandatory. Core §1.3.3 `MUST NOT` generate leap seconds. Receivers are not required to reject them |
| If the AuthnRequest is signed, `Destination` is the URL where the user agent is sent | Service provider | Generate AuthnRequest | Mandatory when the message is signed. Bindings §3.4.5.2 and §3.5.5.2 |
| `RelayState` does not exceed 80 bytes | Service provider | Generate AuthnRequest | Mandatory prohibition. Bindings §3.4.3, §3.5.3, and HTTP-POST-SimpleSign CD-04 §2.3. Integrity protection remains a recommendation |
| HTTP-Redirect removes a protocol `ds:Signature`, raw-DEFLATEs the rest, and signs `SAMLRequest`, `RelayState` when present, then `SigAlg` | Service provider | Generate AuthnRequest | Mandatory. Bindings §3.4.4.1. The typed AuthnRequest writer supplies XML without an embedded signature. An absent `RelayState` is omitted |
| HTTP-POST-SimpleSign signs the raw XML octets, then `RelayState` when present, then `SigAlg` | Service provider | Generate AuthnRequest | Mandatory when that binding is used. CD-04 §2.5 and §2.6. An XML signature inside the message stays |
| Do not emit `AllowCreate` when the requested name-identifier format is `transient` | Service provider | Generate AuthnRequest | Mandatory prohibition. Core §3.4.1.1 as replaced by Errata 05 E14 |
| Sign the AuthnRequest | Service provider | Generate AuthnRequest | Optional for this profile. Profiles §4.1.4.1 says the request `MAY` be signed as directed by the binding. Bindings §3.4.5.2 and §3.5.5.2 say the encoded message `MAY` be signed. Core §3.4.1's general `SHOULD` is not applied on top of that profile rule. Stays off unless `AuthnRequestSigningPolicy::Sign`, which also publishes `AuthnRequestsSigned="true"` in the service provider metadata. Metadata §2.4.4, as amended by Errata 05 E7, then obligates an identity provider to reject an unsigned request from this service provider; see [acceptance rules](web-browser-sso-acceptance.md#identity-provider). A signing service provider signs whatever the identity provider's `WantAuthnRequestsSigned`. Metadata §2.4.3, as amended by Errata 05 E7, says that flag tells service providers whether to expect an unsigned request to be accepted, and that the service provider is not obligated to sign. Library policy: when `WantAuthnRequestsSigned` is true and the service provider does not sign, `start_sso` and `create_login_request` return `SamlError::AuthnRequestSigningRequired` and build no request. E7 does not require that refusal, but says the service provider can reasonably expect an unsigned request to be rejected |
| `ForceAuthn` | Service provider | Generate AuthnRequest | Optional. Core §3.4.1, default false when omitted. Stays omitted unless `StartSso::force_authn` |
| `RequestedAuthnContext` | Service provider | Generate AuthnRequest over HTTP-Redirect, HTTP-POST, or SimpleSign | Optional, omitted unless `StartSso::requested_authn_context`. Core §§3.4.1 and 3.3.2.2.1, with [Errata 05 E45](https://docs.oasis-open.org/security/saml/v2.0/errata05/os/saml-v2.0-errata05-os.html). The protocol schema requires one or more class references or one or more declaration references. The constructor rejects empty and mixed lists. Generation checks absolute URIs, keeps reference order, writes the explicit comparison, and places the element after `NameIDPolicy` (and `Conditions`, if present), before `Scoping`. The selected request signature covers it. [saml2int SDP-SP07](https://kantarainitiative.github.io/SAMLprofiles/saml2int.html#authentication-contexts) is a deployment-profile rule: use `exact` with the required class references, or omit the element when no specific class is required. It is not an OASIS requirement |
| `IsPassive` | Service provider | Generate AuthnRequest over HTTP-Redirect, HTTP-POST, or SimpleSign | Optional. Core §3.4.1. Omitted unless `StartSso::passive`; omission means false. A true value requires the responding IdP and user agent to avoid visibly taking control of the requester's interface; when `ForceAuthn` is also true, fresh authentication must meet that passive constraint |
| `ProviderName` | Service provider | Generate AuthnRequest over HTTP-Redirect, HTTP-POST, or SimpleSign | Optional. Core §3.4.1 and protocol schema `AuthnRequestType`. `StartSso::provider_name` writes the requester's human-readable name only when set, with XML escaping. The `xs:string` type allows an empty name, which is sent. A character XML 1.0 forbids cannot be written, so `start_sso` returns `Invalid` for it, the rule `start_paos_sso` applies to `ecp:Request`. |
| Identifier creation (`AllowCreate="true"`) | Service provider | Generate AuthnRequest | Optional capability. Errata 05 E14 says a requester that does not make specific use of the attribute `SHOULD` generally set it to true, and the schema default is false when the attribute is omitted. `NameIdCreationPolicy` is that specific use. The capability stays off (`AllowCreate="false"`) unless `NameIdCreationPolicy::AllowCreate`. It is not emitted at all for a transient format. An omitted `Format` leaves the identity provider free to choose the identifier format (Core §3.4.1.1). A typed service provider with no configured format advertises and requests `emailAddress` |
| `NameIDPolicy` `Format` is omitted or an absolute URI reference | Service provider | Generate AuthnRequest | Mandatory. Core §1.3.2, as read in [identifiers](identifiers.md#name-identifier-formats). The first configured NameID format is checked. |
| `Cache-Control: no-cache, no-store` and `Pragma: no-cache` | Service provider | HTTP | Recommendation. Bindings §3.4.5.1 and §3.5.5.1, and HTTP-POST-SimpleSign CD-04 §2.7.1. `Outbound::headers` includes those values for the redirect, the POST form, and the SimpleSign form. saml-rs does not send the HTTP response |

## Identity provider Response

| Rule | Actor | Direction | Level |
| --- | --- | --- | --- |
| An error `Response` carries the caller-supplied status and no assertions | Identity provider | Generate Response | Mandatory prohibition on assertions. Profiles §4.1.4.2, which E26 does not replace: if the identity provider returns an error, it MUST NOT include any assertions. Profiles §4.1.4.1 requires that response when the request cannot be satisfied, including when the requested subject is not recognized. Core §3.4.1.4 requires a `Status` describing the error when the presenter cannot be authenticated, the requested subject is not recognized, or local policy prevents an assertion. `SsoOutcome::Failure` writes the `Status` the caller passes and no assertion. The caller chooses any subordinate code, such as `NoPassive` or `AuthnFailed`. The library does not infer one. |
| A `Success` response contains at least one assertion | Identity provider | Generate Response | Mandatory. Profiles §4.1.4.2 / E26: a response that does not return an error MUST contain at least one assertion. `SsoOutcome::Success` carries the `SsoAssertion` the caller passes. `SsoOutcome::Failure` with a top-level `Success` status returns `SamlError::Invalid` from `respond_sso` and `initiate_sso` |
| Error `Response` `Issuer`, `InResponseTo`, and `Destination` follow the successful response | Identity provider | Generate Response | The successful-response rows below. `Issuer` is always present. A solicited `InResponseTo` matches the `AuthnRequest` `ID` (Core §3.2.2). An unsolicited `InResponseTo` is omitted (Core §3.2.2 and Profiles §4.1.5). `Destination` is the assertion consumer service URL |
| An unsolicited error `Response` can be written | Identity provider | Generate unsolicited Response | Library policy for a case the profile leaves open. Profiles §4.1.4.2 forbids assertions in an error response and describes a response that is not associated with a request only for the successful case. Core §3.2.2 requires `InResponseTo` to be absent when the `ID` of a request cannot be determined, for example because the request is malformed. `initiate_sso` and `initiate_sso_artifact` take `SsoOutcome::Failure`, so that an identity provider can report the failure of a login it started, or answer a request it could not read. The response follows the row above and goes to the default assertion consumer service |
| HTTP-POST signs an error `Response` | Identity provider | Generate Response | Library policy. Profiles §4.1.4.5 as replaced by E26 protects each assertion by a signature on the assertion or the `Response`. An error `Response` has no assertion, so that requirement does not apply. Typed HTTP-POST still signs the `Response`, which is how a signed message carries `Destination` (Bindings §3.5.5.2). HTTP-POST-SimpleSign keeps its detached signature over the response octets |
| A successful response contains at least one bearer assertion with an `AuthnStatement` | Identity provider | Generate Response | Mandatory. Profiles §4.1.4.2 as replaced by Errata 05 E26, including a response that is not tied to a request |
| `AuthnInstant` and `AuthnContext` accompany that statement | Identity provider | Generate Response | Mandatory by schema once the statement is emitted: Core §2.7.2 requires the `AuthnInstant` attribute and the `AuthnContext` child of `AuthnStatement`. Core §2.7.2 defines `AuthnInstant` as the time at which the authentication took place. `SsoAssertion::with_authn_instant` writes the time the caller passes, such as the start of a reused identity provider session. The library formats it in UTC to the second, rounded down, so it satisfies Core §1.3.3 and is never a leap second. A value later than the response `IssueInstant` returns `Invalid`, which is library policy: an assertion cannot report an authentication after it was issued. A time before year 1 returns `Invalid`, which is library policy: the formatter writes a four-digit non-negative year. Without the option, `AuthnInstant` is the assertion `IssueInstant`, which is library policy. The context is the class or declaration reference passed to `SsoAssertion::with_authn_context`. Without one, it is the class `urn:oasis:names:tc:SAML:2.0:ac:classes:unspecified`, the Authentication Context class for unspecified means |
| With `exact` comparison, the statement's authentication context is one of the requested references | Identity provider | Generate solicited Response | Mandatory. Core §3.3.2.2.1: when `Comparison` is `exact` or omitted, the resulting context MUST exactly match one of the requested contexts. A success response whose context, or the unspecified class when none is set, is not a requested reference of the same kind returns `Invalid`. For `minimum`, `better`, and `maximum`, strength is "as deemed by the responder", so the caller judges them and the library does not check |
| The subject identifier uses the standard `NameIDPolicy` `Format` the service provider requested | Identity provider | Generate solicited Response | Mandatory for each issued assertion when the request names a Core §8.3 format other than `unspecified`. Compare the effective `NameID` format after XML Schema `xs:anyURI` whitespace collapse on both values. If the request has no format or names `unspecified`, the policy does not constrain the format. Deployments interpret other format URIs under their own rules. A mismatch returns `SamlError::NameIdPolicyFormatMismatch`. When the IdP cannot meet the policy, the caller returns an error `Response` with no assertions and may include `InvalidNameIDPolicy`. [Core §§1.3.2 and 3.4.1.1](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf), [Errata 05 E15](https://docs.oasis-open.org/security/saml/v2.0/errata05/os/saml-v2.0-errata05-os.html), and [protocol schema `NameIDPolicyType`](https://docs.oasis-open.org/security/saml/v2.0/saml-schema-protocol-2.0.xsd). |
| The subject identifier carries the requested `SPNameQualifier` when a specific Core §8.3 format is requested | Identity provider | Generate solicited Response | Mandatory when `NameIDPolicy` includes `SPNameQualifier` and names a Core §8.3 format other than `unspecified`. The qualifier on each issued identifier must match exactly. The schema type is `xs:string`. A mismatch returns `SamlError::Invalid`. The caller decides whether it can serve the requested namespace, such as an affiliation. Core §8.3.6 forbids qualifiers on an entity identifier. If the request combines the `entity` format with `SPNameQualifier`, the caller returns a failure outcome. [Core §3.4.1.1 and Errata 05 E15](https://docs.oasis-open.org/security/saml/v2.0/errata05/os/saml-v2.0-errata05-os.html). |
| A request for the special `encrypted` format requires `EncryptedID` in each issued assertion subject | Identity provider | Generate solicited Response | Mandatory when `NameIDPolicy` requests `encrypted`. The caller chooses the underlying identifier type. Enable `IdentifierEncryptionPolicy::EncryptIdentifiers` and use the encryption certificate in the SP metadata. With identifier encryption disabled, success returns `SamlError::NameIdPolicyRequiresEncryptedId` even if assertion encryption is enabled. [Core §3.4.1.1 and Errata 05 E6 and E15](https://docs.oasis-open.org/security/saml/v2.0/errata05/os/saml-v2.0-errata05-os.html), [assertion schema `SubjectType`](https://docs.oasis-open.org/security/saml/v2.0/saml-schema-assertion-2.0.xsd). |
| With a requested `Subject` that has an identifier, the assertion `Subject` strongly matches it | Identity provider | Generate solicited Response | Mandatory. Core §3.4.1.4 as amended by Errata 05 E75: the resulting assertions' `<Subject>` MUST strongly match the request `<Subject>` (Core §3.3.4), except that the identifier MAY be in a different format if specified by `<NameIDPolicy>`, and an identity provider that cannot or will not produce such assertions MUST return an error `<Status>`. Profiles §4.1.4.1 requires an error response with no assertions when the identity provider does not recognize the principal as the requested identity. A success response returns `Invalid` unless the issued `NameId` has the requested `<NameID>` value, `Format`, `NameQualifier`, `SPNameQualifier`, and `SPProvidedID`. An omitted `Format` is `unspecified` (Core §2.2.2), and `Format` is compared after `xs:anyURI` whitespace collapsing. A `NameId` whose `Format` is the `NameIDPolicy` `Format`, when that differs from the requested one, is not compared: the caller decides that it names the same principal. A requested `<BaseID>` cannot be strongly matched by the `<NameID>` this library issues, so a success response returns `Invalid`. Library policy: a requested `<EncryptedID>` that was not decrypted also returns `Invalid` for a success response, because the identity provider cannot show the match, and the `NameIDPolicy` format exception is not applied to a requested `<BaseID>` or an undecrypted `<EncryptedID>`. A `Subject` with only `<SubjectConfirmation>` names the presenter and is not checked. Requested `<SubjectConfirmation>` elements are not compared; Profiles §4.1.4.1 forbids the service provider from sending them. An error `Response` carries no assertion and is not checked. Whether the authenticated presenter is the requested principal is the caller's decision |
| `NameQualifier`, `SPNameQualifier`, and `SPProvidedID` of the issued `NameId` are written on the assertion `NameID` | Identity provider | Generate Response | Schema `NameIDType` declares them as optional attributes, of type `string` for the qualifiers. Each value is written as given, escaped as an attribute value, and omitted when unset. |
| When no requested context can be met, answer top-level `Responder`, optionally with `NoAuthnContext` | Identity provider | Generate Response | Mandatory top-level code, optional subordinate code. Core §3.3.2.2.1 as replaced by Errata 05 E65. The caller decides that the request cannot be met and passes `SsoOutcome::Failure` with `Status::responder()` and `SubordinateStatusCode::no_authn_context()` to `respond_sso` or `respond_paos_sso` |
| `SessionIndex` on each authentication statement when this identity provider supports Single Logout | Identity provider | Generate Response | Mandatory when Single Logout is supported. Profiles §4.1.4.2 / E26. Support here means the identity provider metadata advertises `SingleLogoutService`. The value is the assertion `ID`, one of the two approaches Core §2.7.2 lists as `RECOMMENDED` for privacy. No `SessionIndex` is emitted when logout is not advertised. `Outbound<SsoResponse>::session_index` and `PaosHttpResponse<SsoResponse>::session_index` return the value written, including for an encrypted assertion or an artifact |
| Bearer `SubjectConfirmationData` has `Recipient` and `NotOnOrAfter`, and no `NotBefore` | Identity provider | Generate Response | Mandatory. Profiles §4.1.4.2 / E26 |
| Additional `SubjectConfirmation` elements in a bearer assertion | Identity provider | Generate Response | Optional, not supported. Profiles §4.1.4.2 / E26: bearer assertions MAY contain additional `<SubjectConfirmation>` elements, and their processing is outside the profile. The assertion carries only the bearer confirmation this library writes. `respond_sso`, `initiate_sso`, `respond_sso_artifact`, `initiate_sso_artifact`, and `respond_paos_sso` take an `SsoAssertion` built from the `NameId` of the subject, so a caller cannot supply a confirmation. The holder-of-key Web Browser SSO profile is not claimed |
| Assertion `NameID` `Format` is omitted or an absolute URI reference | Identity provider | Generate Response | Mandatory. Core §1.3.2 requires a URI reference value to have at least one non-whitespace character and to be absolute, as read in [identifiers](identifiers.md#name-identifier-formats). A `NameId` format or configured format that is not one is `SamlError::Invalid`. Core §2.2.2 with Errata 05 E60 makes `Format` optional and puts `unspecified` in effect when it is omitted. A `NameId` without a format is written with the first configured NameID format. With none configured, `Format` is omitted. This is a producer rule: an inbound empty `Format` is not rejected |
| Bearer assertion `Issuer` is the responding identity provider, with `Format` omitted or `entity` | Identity provider | Generate Response | Mandatory. Profiles §4.1.4.2 / E26 |
| Bearer assertion includes `AudienceRestriction` for the service provider | Identity provider | Generate Response | Mandatory. Profiles §4.1.4.2 / E26 |
| Response `Issuer` is present when the response is signed or an assertion is encrypted | Identity provider | Generate Response | Mandatory when that condition holds. Errata 05 E17. Typed responses always include it |
| Solicited response `InResponseTo` matches the AuthnRequest `ID` | Identity provider | Generate Response | Mandatory. Core §3.2.2. The same match is required on bearer `SubjectConfirmationData` by Profiles §4.1.4.2 / E26 |
| Unsolicited response omits `InResponseTo` | Identity provider | Generate Response | Mandatory prohibition. Core §3.2.2 and Profiles §4.1.5. Bearer subject confirmation data omits it as well: Profiles §4.1.5 says it should not be present, and E26 requires the service provider to verify that it is absent |
| A request without an ACS URL, ACS index, or `ProtocolBinding` uses the metadata default `AssertionConsumerService` | Identity provider | Generate solicited Response | Mandatory. Core §3.4.1; Profiles §4.1.4.1 and §4.1.6. Metadata §§2.2.3, 2.4.1 and E37 scope the default to the SP role advertising SAML 2.0 in `protocolSupportEnumeration`, before binding filtering. An unsupported default or incompatible response binding returns `Invalid` |
| Apply the indexed-default algorithm to ACS candidates | Metadata consumer | Endpoint selection | Metadata §2.2.3. The default is the first `isDefault` true, otherwise the first not explicitly false, otherwise the first. The unqualified XML Schema boolean accepts `true`, `1`, `false`, and `0` with surrounding XML whitespace. Foreign attributes do not set the flag |
| Read `WantAuthnRequestsSigned`, `AuthnRequestsSigned`, and `WantAssertionsSigned` as XML Schema booleans | Metadata consumer | Generate AuthnRequest or Response, receive AuthnRequest | Mandatory. The metadata schema types each attribute `boolean`, and Metadata §§2.4.3 and 2.4.4 read an omitted one as false. `true` and `1` are true, and `false` and `0` are false, with surrounding XML whitespace. Another value is read as false |
| Deliver an unsolicited response to the metadata default `AssertionConsumerService` | Identity provider | Generate unsolicited Response | Recommendation. Profiles §4.1.5. Typed `initiate_sso` and `initiate_sso_artifact` use the global default above. An unsupported default or incompatible response binding returns `Invalid`. There is no recommendation relaxation in this API |
| Select an ACS when generating an explicit ACS URL, or when the request specifies a response binding | Service provider or identity provider | Generate AuthnRequest or Response | Library selection policy. The binding-specific helper applies the indexed-default algorithm to that binding's candidates. `start_sso` emits the chosen URL and `ProtocolBinding`, so the request explicitly identifies its endpoint. Raw binding-specific metadata access remains a lower-level lookup |
| HTTP-POST protects each assertion by a signature on the assertion or on the response | Identity provider | Generate Response | Mandatory for HTTP-POST. Profiles §4.1.4.5 as replaced by E26, and §4.1.3.5 as replaced by E93. Existing typed POST signing already does this |
| Sign a response that contains a CBC `EncryptedAssertion` | Identity provider | Generate Response | Recommendation. Errata 05 E93. Starts enabled on `RespondSso::post`, `RespondSso::simple_sign`, and `RespondSso::artifact`. `RespondSso::allow_unsigned_encrypted_cbc` relaxes that recommendation alone. It does not add a receiver rejection; a relying party that already requires the signature still rejects the relaxed response |
| Assertion encryption | Identity provider | Generate Response | Optional. Stays off unless `XmlEncryptionPolicy::assertions` is `EncryptAssertions` |
| `<EncryptedID>` in place of the assertion `<NameID>` when the request leaves identifier encryption to the IdP | Identity provider | Generate Response | Optional. Core §§2.2.4 and 3.4.1.1. Select `IdentifierEncryptionPolicy::EncryptIdentifiers` on `XmlEncryptionPolicy::identifiers`. This setting selects only identifier encryption. The IdP encrypts each subject `NameID` with the SP metadata encryption certificate. Each `<NameID>` is replaced in the same location in the subject (Core §6.1). To encrypt the identifier in a `LogoutRequest`, set `StartSlo::identifier_encryption`. See [Single Logout](single-logout.md#encrypted-principal-identifier). |
| `<EncryptedAttribute>` in place of each assertion `<Attribute>` | Identity provider | Generate Response | Optional. Core §2.7.3.2. Stays off unless `XmlEncryptionPolicy::attributes` is `EncryptAttributes`, which does not select identifier or assertion encryption. Each `<Attribute>` of each `<AttributeStatement>` is replaced in the same location (Core §6.1) |
| `EncryptedData` carries `Type`, its value is `http://www.w3.org/2001/04/xmlenc#Element`, and its content is the element it replaces | Identity provider | Generate `<EncryptedID>` or `<EncryptedAttribute>` | Core §§2.2.4, 2.7.3.2, and 6.1. A present `Type` is a recommendation, on, with no relaxation: `Type` is always written. Its value, and content of `NameIDType` or `AttributeType`, are mandatory. The plaintext is the inclusive canonical form of the `<NameID>` or `<Attribute>`, so it declares every namespace in scope. That serialization is library policy. The key is the service provider's metadata encryption certificate, as for `EncryptedAssertion` |
| Encrypt the `<NameID>` or `<Attribute>` before the assertion or response is signed | Identity provider | Generate Response | Library policy. Original Core §6.2 required this order, and Errata 05 E43 and E93 replace that section. The signature is calculated after encryption, so it covers the ciphertext. When assertion encryption is also selected, the signed assertion that carries the encrypted elements is then encrypted |
| `<xenc:EncryptedKey>` is in the `ds:KeyInfo` of `EncryptedData` | Identity provider | Generate `<EncryptedID>` or `<EncryptedAttribute>` | Core §6.2 as replaced by Errata 05 E43 allows an encrypted key embedded in `EncryptedData`. No sibling `EncryptedKey` is written, so the Core §2.2.4 and §2.7.3.2 `Recipient` recommendation for those children does not apply. The key placement is the one `EncryptedAssertion` uses |
| Do not generate a leap-second time | Identity provider | Generate any instant | Mandatory. Core §1.3.3 |
| Return the exact `RelayState` received with the `AuthnRequest` | Identity provider | Generate Response | Mandatory. Bindings §3.1.1, §3.4.3, §3.5.3, and HTTP-POST-SimpleSign CD-04 §2.3. `respond_sso` writes the RelayState of `Received<AuthnRequest>`: absent, empty, and a value stay distinct. `RespondSso::relay_state` on a request that carried RelayState returns `SamlError::ProtocolProfile`. When the request carried none, or on `initiate_sso`, Bindings §3.4.3 lets the identity provider include RelayState, and `RespondSso::relay_state` sets it |
| `RelayState` does not exceed 80 bytes | Identity provider | Generate Response | Mandatory prohibition for a value the identity provider sets with `RespondSso::relay_state`, including on `initiate_sso`. Bindings §3.5.3 and HTTP-POST-SimpleSign CD-04 §2.3. A value received with the `AuthnRequest` is returned unchanged even when longer, because Bindings §3.4.3, §3.5.3, and HTTP-POST-SimpleSign CD-04 §2.3 require the responder to return the exact data it received |
| HTTP-POST-SimpleSign signs the raw XML octets, then `RelayState` when present, then `SigAlg` | Identity provider | Generate Response | Mandatory when that binding is used. CD-04 §2.5 and §2.6. An assertion signature stays |
| `Cache-Control: no-cache, no-store` and `Pragma: no-cache` | Identity provider | HTTP | Recommendation. Bindings §3.5.5.1 and HTTP-POST-SimpleSign CD-04 §2.7.1. `Outbound::headers` includes those values for the POST form and the SimpleSign form. saml-rs does not send the HTTP response |

Direct Assertion signatures and the RSA-SHA2 XML signature profile are
library hardening on acceptance. They are not turned on by these producer
rules.

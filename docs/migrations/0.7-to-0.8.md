# How to upgrade from 0.7 to 0.8

This guide moves an integration of `saml-rs`, `opensaml`, `samlify`, or
`samlet` from the latest `0.7.x` release to `0.8.x`. The compatibility crates
re-export the same API, so every step applies to them too. Compatible
additions are in the [changelog](../../CHANGELOG.md).

Work through it in this order:

1. [Fix compile errors](#1-fix-compile-errors). The compiler finds these for
   you.
2. [Check the signature and trust defaults](#2-check-the-signature-and-trust-defaults).
   They change what `recommended()` accepts, so most deployments read this
   part.
3. Read the parts for the roles and features you use:
   [service provider](#3-service-provider),
   [identity provider](#4-identity-provider),
   [metadata](#5-metadata),
   [logout and name identifier management](#6-single-logout-and-name-identifier-management),
   and [XML, SOAP, and bindings](#7-xml-soap-and-bindings).
4. Skim [smaller changes](#8-smaller-changes-you-may-notice) if you compare
   outputs or match specific errors.

Each section starts with **Affects**. Skip the section when it does not
describe your integration.

### 1.1 Replace the collection helpers

**Affects:** callers of these `saml_rs::util` items, including through the
compatibility crates. Typed `Saml<Sp>` and `Saml<Idp>` operations are not
affected.

| Removed | Replacement |
| --- | --- |
| `OneOrMany::One(value)` | `vec![value]` |
| `OneOrMany::Many(values)` | `values` (a `Vec<T>`) |
| `OneOrMany::into_vec()` | Store a `Vec<T>` directly |
| `cast_array_opt(value)` | `value.unwrap_or_default()` on an `Option<Vec<T>>` |
| `is_non_empty_array(items)` | `!items.is_empty()` |
| `verify_fields(field, meta_field)` | `!field.is_empty() && field.iter().all(\|value\| value == meta_field)` |
| `last(items)` | `items.last()` |

Keep the empty-input mismatch when you replace `verify_fields`. If your
application needs a single-or-many input type, define it in the application.

### 1.2 Pass `RespondPaosSso` to `respond_paos_sso`

**Affects:** identity providers that answer Enhanced Client/Proxy login with
`Saml<Idp>::respond_paos_sso`. Service providers and `reject_paos_sso` callers
need no change.

**Now:** `respond_paos_sso` takes a fourth argument. `RespondPaosSso::default()`
keeps the previous response, which has no `AttributeStatement`:

```rust
let answered = idp.respond_paos_sso(&sp, &received, subject, RespondPaosSso::default())?;
```

To send attributes, set them on the options. They are written the same way as
`RespondSso::attributes`:

```rust
let answered = idp.respond_paos_sso(
	&sp,
	&received,
	subject,
	RespondPaosSso::default().attributes(attributes),
)?;
```

`respond_paos_sso` returns `SamlError::Invalid` when these attributes are
combined with a login response template, or when a basic attribute name is not
an XML name.

### 1.3 Drop `RespondSlo::relay_state`

**Affects:** callers of `RespondSlo::relay_state`.

**Before:** the setter could replace or drop the RelayState of a logout
response.
**Now:** `respond_slo` always writes the exact RelayState that arrived with the
`LogoutRequest`, as Bindings §3.1.1 requires of a responder.

**Upgrade:** remove the call. If you passed the received or stored RelayState
back, the response is unchanged:

```rust
let response = idp.respond_slo(&sp, &received, RespondSlo::post())?;
```

If you replaced or suppressed the RelayState, keep that state on your side,
for example in a session keyed by the RelayState you sent. You can no longer
add a RelayState to a response whose request had none.

`RespondSlo::soap` still returns `SamlError::ProtocolProfile` for a request
that carried RelayState, because SOAP cannot return it. Suppressing the
RelayState no longer avoids that error. Answer that request over a
front-channel binding.

### 1.4 Give `IssuedArtifacts` a lifetime

**Affects:** identity providers that issue artifacts with `issue_artifact`,
`respond_sso_artifact`, or `initiate_sso_artifact`.

**Before:** `IssuedArtifacts::new()` and `Default` built a store in which an
unresolved artifact stayed resolvable until you called
`IssuedArtifacts::remove`.
**Now:** both are removed. Build the store with a lifetime:

```rust
use std::time::Duration;

use saml_rs::IssuedArtifacts;

let mut issued = IssuedArtifacts::expire_after(Duration::from_secs(60));
```

An `ArtifactResolve` that arrives after the lifetime gets Success without the
message, and `AnsweredArtifact::release` reports
`ArtifactWithheld::NotOutstanding`. Each issue drops the artifacts issued more
than one lifetime ago, so you no longer need `remove` to bound memory.

**Choose the lifetime:** SAML Core §3.5.3 asks the issuer for the shortest
practical time limit. Use the time a service provider needs to receive the
artifact and send `ArtifactResolve`. On the service provider, keep the
`ArtifactUses::enforce_single_use` period longer than that lifetime.

### 1.5 Remove the software RSA key-transport opt-in

**Affects:** callers of
`XmlEncryptionPolicy::allow_insecure_software_rsa_key_transport_decryption`
or `XmlEncryptionPolicy::with_insecure_software_rsa_key_transport_decryption_allowed`,
code that sets `allow_insecure_software_rsa_key_transport_decryption` on
`EntitySetting`, `FlowOptions`, or `AssertionDecryptionOptions`, and every
`crypto-rustcrypto` build with a decryption key.

**Upgrade:** delete the call or the assignment. Replace the
`allow_insecure_software_rsa_key_transport_decryption()` constructor with
`XmlEncryptionPolicy::default()` or the constructor you want:

```rust
use saml_rs::{XmlEncryptionPolicy, XmlPolicy};

let xml = XmlPolicy {
    encryption: XmlEncryptionPolicy::encrypt_assertions(),
    ..XmlPolicy::default()
};
```

**Behaviour:** on `crypto-rustcrypto`, RSA key transport now runs in
`kryptering` on `rsa` 0.10, which RustSec lists as patched for
RUSTSEC-2023-0071. With a decryption key configured, these now decrypt with
the default options, as they already did on `crypto-aws-lc`: an encrypted
assertion, `<EncryptedID>`, `<EncryptedAttribute>`, `<NewEncryptedID>`, and
the `<EncryptedID>` of a `LogoutRequest` or `AuthnRequest`.

| Without the opt-in on `crypto-rustcrypto` | Before | Now |
| --- | --- | --- |
| Encrypted element received | `SamlError::Unsupported` | Decrypted |
| `ManageNameIDRequest` with an encrypted identifier | Refused with `NameIdManagementRefusal::UndecryptableIdentifier` or `UndecryptableNewIdentifier` | Decrypted |

If you relied on that refusal, configure no decryption key for the entity.

RSA-v1.5 key transport still needs
`XmlEncryptionPolicy::with_rsa15_key_transport_decryption_allowed` and
`crypto-legacy-algorithms`. It no longer needs the removed opt-in.

### 1.6 Replace `FlowOptions::strict_xml_signature_profile`

**Affects:** raw flows that set `FlowOptions::strict_xml_signature_profile`.

**Now:** the `bool` is replaced by `FlowOptions::xml_signatures`, an
`XmlSignatureProfile`.

| Before | Now |
| --- | --- |
| `strict_xml_signature_profile: true` | `xml_signatures: XmlSignatureProfile::StrictRsaSha2` |
| `strict_xml_signature_profile: false` (default) | `xml_signatures: XmlSignatureProfile::AllowProviderSupportedForCompatibility` (default) |

What `StrictRsaSha2` now also checks is in
[section 2.2](#22-expect-strictrsasha2-on-detached-and-identity-provider-signatures).

### 1.7 Complete struct literals

**Affects:** a struct literal that names every field and does not end with
`..Default::default()` or the listed preset.

| Struct | New field | Value that keeps 0.7 behaviour |
| --- | --- | --- |
| `Credentials` | `additional_decryption_keys: Vec<DecryptionCredential>` | `Vec::new()` |
| `Credentials` | `additional_signing_certificates: Vec<CertificatePem>` | `Vec::new()` |
| Typed and raw `SpMetadataConfig`, `IdpMetadataConfig` | `lifetime: Option<MetadataLifetime>` | `None` |
| Typed and raw `SpMetadataConfig`, `IdpMetadataConfig` | `organization: Option<Organization>` | `None` |
| Typed and raw `SpMetadataConfig`, `IdpMetadataConfig` | `contacts: Vec<ContactPerson>` | `Vec::new()` |
| Typed and raw `SpMetadataConfig`, `IdpMetadataConfig` | `error_url: Option<String>` | `None` |
| `IdpValidationPolicy` | `xml_signatures: XmlSignatureProfile` | `AllowProviderSupportedForCompatibility` |

Prefer ending the literal with `..Credentials::default()`,
`..Default::default()`, or `..IdpValidationPolicy::recommended()`.

For raw metadata configs, `..Default::default()` initializes all three
description fields to the values above. Typed metadata configs do not implement
`Default`. Use `SpMetadataConfig::new(acs_endpoints)` or
`IdpMetadataConfig::new(sso_endpoints)`, or add the fields to your literal.
Existing config builder calls need no change. Empty description fields preserve
the previous metadata output. When populated, invalid organization, contact,
or error URI inputs return `SamlError::Invalid` during generation.

**`lifetime`:** `None` keeps metadata without `validUntil` and
`cacheDuration`. Metadata §2.3.1 and §2.3.2 require one of them on the root
element, so prefer setting it. The config builders take the same value through
`metadata_lifetime`:

```rust
use std::time::Duration;
use saml_rs::MetadataLifetime;

let lifetime = Some(MetadataLifetime::CacheDuration(Duration::from_secs(86_400)));
```

A `MetadataLifetime::ValidUntil` instant is fixed when `Saml` is built. Build a
new `Saml` before it passes, or use `MetadataLifetime::CacheDuration`.

**`xml_signatures` on `IdpValidationPolicy`:** `compatibility()` sets
`AllowProviderSupportedForCompatibility`, so an identity provider on that
preset verifies what it verified before. `recommended()` sets
`ExcludeWeakAlgorithms` ([section 2.1](#21-stop-relying-on-md5-ripemd-160-and-short-rsa-keys-under-recommended)).
With `StrictRsaSha2`, the identity provider applies the profile to the
`AuthnRequest` and logout messages it receives:

```rust
use saml_rs::{IdpValidationPolicy, XmlSignatureProfile};

let validation = IdpValidationPolicy {
    xml_signatures: XmlSignatureProfile::StrictRsaSha2,
    ..IdpValidationPolicy::recommended()
};
```

**`additional_decryption_keys`:** the field rolls over an encryption key
without downtime:

1. Put the next key and its certificate in a `DecryptionCredential` in the
   list. Metadata publishes both certificates, and decryption tries
   `decryption_key` first, then each additional key.
2. Make the next key the `decryption_key` and `encryption_certificate`, and
   move the old key and certificate into the list. A peer that encrypts for
   the first published certificate, as saml-rs does, now uses the new one.
3. Once every peer has refreshed your metadata, remove the old key.

A non-empty list without a `decryption_key` returns
`SamlError::MissingKey("decryption_key")` from the config builders.

### 1.8 Extend exhaustive matches

| Enum | Add an arm for | Meaning |
| --- | --- | --- |
| `XmlSignatureProfile` | `ExcludeWeakAlgorithms` | [Section 2.1](#21-stop-relying-on-md5-ripemd-160-and-short-rsa-keys-under-recommended) |
| `MetadataTrustPolicy` | `RequireSignatureAllowingWeakAlgorithmsForCompatibility { trusted_certificates }` | [Section 2.5](#25-stop-relying-on-md5-ripemd-160-and-short-rsa-keys-in-signed-metadata) |
| `DataEncryptionAlgorithm` | `Aes256Gcm` | AES-256-GCM content encryption |
| `KeyEncryptionAlgorithm` | `RsaOaep { digest, mgf }` | XML Encryption 1.1 RSA-OAEP with explicit digest and mask generation |

These public enum families now use `#[non_exhaustive]`, including through
the compatibility crates:

| Family | Enums |
| --- | --- |
| Algorithms | `SignatureAlgorithm`, `DigestAlgorithm`, `DataEncryptionAlgorithm`, `KeyEncryptionAlgorithm`, `MaskGenerationFunction`, `TransformAlgorithm` |
| URI formats | `NameIdFormat`, `AttributeNameFormat` |
| Supported transports and parsers | `Binding`, `SsoRequestBinding`, `SsoResponseBinding`, `LogoutBinding`, `NameIdManagementBinding`, `BrowserInput`, `ParserType` |
| Validation and trust profiles | `XmlSignatureProfile`, `MetadataTrustPolicy` |
| Refusal reasons | `NameIdManagementRefusal`, `ArtifactWithheld` |
| Contact extensions | `ContactType` |

Add a catch-all arm even when a `match` covers every current variant.
Existing variants remain constructible. A security decision must reject an
unhandled future variant rather than silently accept it:

```rust
use saml_rs::MaskGenerationFunction as Mgf;

fn digest_name(mgf: Mgf) -> Result<&'static str, &'static str> {
	match mgf {
		Mgf::Mgf1Sha256 => Ok("SHA-256"),
		Mgf::Mgf1Sha384 => Ok("SHA-384"),
		Mgf::Mgf1Sha512 => Ok("SHA-512"),
		_ => Err("unsupported mask generation function"),
	}
}
```

The catch-all covers future variants. It does not make an unsupported
algorithm or binding work. Inside saml-rs, the attribute does not require
catch-all arms. Exhaustive matches can still identify implementations that
need an update.
The [extensibility audit](../research/non-exhaustive-api.md) records why
closed choices and public-field struct construction remain unchanged.

If a match only maps variants to URIs, replace it with `as_uri()`:

```rust
let data_uri = algorithms.data_encryption.as_uri();
let key_uri = algorithms.key_encryption.as_uri();
```

`RsaOaep` carries a `DigestAlgorithm` and a `MaskGenerationFunction`. Keep
both when storing or forwarding the selected algorithm. `as_uri()` returns
the key transport URI without its parameters.

The defaults remain AES-256-CBC and RSA-OAEP-MGF1P. Existing configurations
and raw encryption function signatures are unchanged. Selecting the new
variants requires a crypto provider. Both config builders return
`SamlError::Unsupported` for unsupported OAEP parameters. AWS-LC and FIPS
require matching SHA-256, SHA-384, or SHA-512 digest and MGF1 hashes.

`TimeWindowField` gains `MetadataValidUntil` and
`ManageNameIdRequestIssueInstant`. It is `#[non_exhaustive]`, so a wildcard
arm already covers them.

### 1.9 Bind the RelayState from `finish_name_id_management_redirect`

**Affects:** service providers that call `finish_name_id_management_redirect`
and match its result as `Ok(())`.

**Now:** it returns the received `RelayStateParam` instead of `()`. Code that
ends the call with `?;` compiles unchanged. Otherwise bind the value:

```rust
let relay_state = sp.finish_name_id_management_redirect(&idp, &pending, input, validation)?;
```

Why the value can be present is in
[section 3.8](#38-read-the-relaystate-a-peer-adds-to-a-response).

### 1.10 Update `bergshamra` to 0.12 if you depend on it directly

**Affects:** a crate that also depends on `bergshamra`, for example to name
the `bergshamra::keys::Key` that `saml_rs::crypto::keys::load_private_key`
returns and that `construct_saml_signature`, `construct_message_signature`,
and `decrypt_assertion` take. Integrations that only call `saml-rs` are not
affected.

**Now:** `crypto-rustcrypto`, `crypto-aws-lc`, and `crypto-fips` use
Bergshamra 0.12.0. A `Key` from a `bergshamra` 0.11 dependency is a different
type, so that code no longer compiles. Set `bergshamra = "0.12"` and apply the
[Bergshamra 0.12.0 changelog](https://github.com/kushaldas/bergshamra/blob/v0.12.0/CHANGELOG.md)
to your direct calls.

Through `saml-rs`, RSA keys shorter than 1024 bits behave as in 0.7:

- A peer certificate with such a key verifies no signature on any provider and
  returns `SamlError::Crypto`. Only the error message changes.
- A local private key with such a key still loads, signs, and decrypts on the
  default `crypto-bergshamra` feature. AWS-LC and FIPS still reject it.

## 2. Check the signature and trust defaults

| Change | Affects you if | Section |
| --- | --- | --- |
| Recommended excludes MD5, RIPEMD-160, and RSA keys under 2048 bits | A peer signs with one of them and you use `recommended()` or `Default` | [2.1](#21-stop-relying-on-md5-ripemd-160-and-short-rsa-keys-under-recommended) |
| `StrictRsaSha2` covers detached `SigAlg` and the identity provider | You select `StrictRsaSha2` | [2.2](#22-expect-strictrsasha2-on-detached-and-identity-provider-signatures) |
| `ds:Object` in a message signature is rejected | A peer signs with `ds:Object` | [2.3](#23-expect-dsobject-in-a-message-signature-to-be-rejected) |
| A signature that does not verify rejects an SSO response | An identity provider sends a broken assertion signature | [2.4](#24-expect-a-signature-that-does-not-verify-to-reject-an-sso-response) |
| Signed metadata excludes weak algorithms and short keys | You import signed metadata | [2.5](#25-stop-relying-on-md5-ripemd-160-and-short-rsa-keys-in-signed-metadata) |
| `CertificateMismatch` is no longer returned | You match it | [2.6](#26-handle-signature-verification-errors-instead-of-certificatemismatch) |
| Unsigned `AuthnRequest` from a signing SP is rejected | You run an identity provider on Recommended | [2.7](#27-expect-unsigned-requests-from-a-signing-service-provider-to-be-rejected) |

Compatibility presets and the raw API are unchanged by sections 2.1 to 2.4.

### Relax one peer at a time

Sections 2.1, 2.3, and 2.4 share one relaxation. Ask the peer to fix its
signatures. Until it does, keep Recommended and relax only `xml_signatures`:

```rust
use saml_rs::{SpValidationPolicy, XmlSignatureProfile};

let validation = SpValidationPolicy {
    xml_signatures: XmlSignatureProfile::AllowProviderSupportedForCompatibility,
    ..SpValidationPolicy::recommended()
};
```

The same field exists on `IdpValidationPolicy`. It accepts all three cases at
once: weak algorithms and keys, `ds:Object`, and an unverified assertion
signature beside a verified Response signature.

### 2.1 Stop relying on MD5, RIPEMD-160, and short RSA keys under Recommended

**Affects:** `SpValidationPolicy::recommended`,
`IdpValidationPolicy::recommended`, or their `Default`, with a peer that signs
with MD5, RIPEMD-160, or an RSA key shorter than 2048 bits. Also
`XmlSignatureProfile::StrictRsaSha2` with a peer RSA key shorter than 2048
bits. See
[weak algorithms and keys](../conformance/xml-security-algorithms.md#weak-algorithms-and-keys).

**Before:** Recommended used `AllowProviderSupportedForCompatibility`.
**Now:** Recommended sets `xml_signatures` to the new
`XmlSignatureProfile::ExcludeWeakAlgorithms` on both roles. SHA-1 still
verifies.

- A signature that authenticates the received message, or a detached
  `SigAlg`, that uses RSA-MD5, HMAC-MD5, RSA-RIPEMD160, ECDSA-RIPEMD160,
  HMAC-RIPEMD160, or an MD5 or RIPEMD-160 digest returns
  `SamlError::AlgorithmUnsupported`.
- A signing certificate with an RSA key shorter than 2048 bits is not used to
  verify. When the peer has no other usable key, the message returns
  `SamlError::Crypto`. Otherwise a message signed with the short key fails
  signature verification. `StrictRsaSha2` applies the same key rule.

Only the default build and RustCrypto with `crypto-legacy-algorithms` verified
these before, and for RSA only keys of 1024 bits or more. AWS-LC, FIPS, and
RustCrypto without that feature already rejected them. On those builds a
detached MD5 or RIPEMD-160 `SigAlg` now returns
`SamlError::AlgorithmUnsupported` instead of the provider's
`SamlError::Crypto`.

**Upgrade:** ask the peer to sign with RSA-SHA256 and a 2048-bit key or
larger. Until it does, [relax one peer](#relax-one-peer-at-a-time).

### 2.2 Expect `StrictRsaSha2` on detached and identity provider signatures

**Affects:** callers that select `XmlSignatureProfile::StrictRsaSha2`. See
[inbound XML signature verification](../conformance/xml-security-algorithms.md#inbound-xml-signature-verification).

**Before:** any detached `SigAlg` the crypto provider supported verified, and
`IdpValidationPolicy` had no profile.
**Now:** `StrictRsaSha2` also applies to the detached `SigAlg` of an
HTTP-Redirect or HTTP-POST-SimpleSign message. A `SigAlg` other than
RSA-SHA256, RSA-SHA384, or RSA-SHA512 returns
`SamlError::AlgorithmUnsupported`. An identity provider applies the profile
through `IdpValidationPolicy::xml_signatures`
([section 1.7](#17-complete-struct-literals)).

**Upgrade:** if a peer signs Redirect or SimpleSign messages with RSA-SHA1,
ask it to move to RSA-SHA256, or select
`AllowProviderSupportedForCompatibility`.

`SamlError::AlgorithmUnsupported` now displays `signature algorithm is not
allowed`. Before, it displayed `embedded XML signature algorithm is not
allowed`.

### 2.3 Expect `ds:Object` in a message signature to be rejected

**Affects:** `SpValidationPolicy::recommended`,
`IdpValidationPolicy::recommended`, their `Default`, or
`XmlSignatureProfile::StrictRsaSha2`, with a peer that puts `ds:Object` inside
the signature of a `Response`, `Assertion`, `AuthnRequest`, `LogoutRequest`,
or `LogoutResponse`. See
[metadata trust](../conformance/metadata-and-replay.md#metadata-trust).

**Before:** the message was accepted, and the `ds:Object` content was not
signed.
**Now:** a received message whose authenticating signature contains
`ds:Object` returns `SamlError::SignedReferenceMismatch` on every binding that
carries an XML signature.

**Upgrade:** ask the peer to sign without `ds:Object`. Until it does,
[relax one peer](#relax-one-peer-at-a-time).

### 2.4 Expect a signature that does not verify to reject an SSO response

**Affects:** `SpValidationPolicy::recommended`, its `Default`, or
`XmlSignatureProfile::StrictRsaSha2`, with `finish_sso`,
`accept_unsolicited_sso`, or `finish_paos_sso`. See
[Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md#service-provider).

**Before:** an assertion signature that did not verify was ignored when the
Response signature verified, and HTTP-Redirect and HTTP-POST-SimpleSign
verified only the detached signature.
**Now:** a response returns `SamlError::SignatureVerification` with
`SignatureVerificationReason::XmlSignature` when a signature on the
`Response`, on one of its assertions, or on a decrypted assertion does not
verify. That includes a `Response` signature that verifies only after the
assertions are decrypted. Profiles §4.1.4.3 requires the service provider to
verify any signature present on the response or its assertions.

Under `AssertionSignaturePolicy::RequireSigned`, the same response used to
return `AssertionSignatureRequired`. It now returns this error.

**Upgrade:** ask the identity provider to send signatures that verify with the
keys in its metadata. Until it does,
[relax one peer](#relax-one-peer-at-a-time).

### 2.5 Stop relying on MD5, RIPEMD-160, and short RSA keys in signed metadata

**Affects:** imports with `MetadataTrustPolicy::RequireSignature` or
`RequireSignatureAllowingOtherCanonicalization` of metadata signed with MD5,
RIPEMD-160, or an RSA key shorter than 2048 bits. See
[metadata trust](../conformance/metadata-and-replay.md#metadata-trust).

**Before:** both options verified every algorithm and key the crypto provider
verified.
**Now:** both exclude what Recommended excludes for messages. SHA-1 still
verifies. `UnsignedForCompatibility`, `verify_metadata_signature`, and
`Metadata::verify_signature` are unchanged.

- A metadata signature that uses RSA-MD5, RSA-RIPEMD160, ECDSA-RIPEMD160, or
  an MD5 or RIPEMD-160 digest returns `SamlError::AlgorithmUnsupported`.
- A pinned RSA certificate shorter than 2048 bits is not used to verify. When
  no other pinned certificate loads, the import returns `SamlError::Crypto`.
  Otherwise metadata signed with the short key returns
  `SamlError::SignatureVerification`.

Only the default build and RustCrypto with `crypto-legacy-algorithms` verified
these algorithms or keys before. Other builds reject such metadata as they did
before.

**Upgrade:** ask the publisher to sign with RSA-SHA256 and a 2048-bit key or
larger. Until it does, select the new option, which keeps the signature shape
and transform rules of `RequireSignature`:

```rust
use saml_rs::{CertificatePem, IdpDescriptor, MetadataTrustPolicy};

let certificates = [CertificatePem::new(metadata_signing_certificate_pem)];
let idp = IdpDescriptor::from_metadata_xml_for(
    expected_entity_id,
    &metadata_xml,
    MetadataTrustPolicy::RequireSignatureAllowingWeakAlgorithmsForCompatibility {
        trusted_certificates: &certificates,
    },
)?;
```

No option accepts both an inclusive canonicalization reference transform and
these algorithms.

### 2.6 Handle signature verification errors instead of `CertificateMismatch`

**Affects:** code that matches `SamlError::CertificateMismatch`, or relies on
rejecting a signature whose `KeyInfo` carries a certificate the peer's
metadata does not list. See
[metadata trust](../conformance/metadata-and-replay.md#metadata-trust).

**Now:** verification no longer compares the certificate in `KeyInfo` with the
trusted certificates. A signature verifies when a trusted key verifies it. No
signature verification returns `SamlError::CertificateMismatch`.

| Signature | Before | Now |
| --- | --- | --- |
| By a trusted key, `KeyInfo` carries another certificate (such as a re-issued certificate for the same key pair) | `CertificateMismatch` | Verifies |
| By another key, typed flows and `MetadataTrustPolicy::RequireSignature` | `CertificateMismatch` when `KeyInfo` carried a certificate | `SignatureVerification` with `SignatureVerificationReason::XmlSignature` |
| By another key, `verify_signature` and `verify_metadata_signature_detailed` | `CertificateMismatch` when `KeyInfo` carried a certificate | Reported as not verified |

**Upgrade:** handle `SignatureVerification`, or an unverified result, where
you handled `CertificateMismatch`.

### 2.7 Expect unsigned requests from a signing service provider to be rejected

**Affects:** identity providers on `IdpValidationPolicy::recommended`, its
`Default`, or `AuthnRequestValidationPolicy::AllowUnsignedVerifyIfPresent`
that call `receive_sso` or `receive_paos_sso` with an `SpDescriptor` whose
metadata sets `AuthnRequestsSigned="true"`. See
[Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md#identity-provider).

**Before:** an unsigned `AuthnRequest` from that service provider was
accepted.
**Now:** it returns `SamlError::SignatureMissing`. Metadata §2.4.4, as amended
by Errata 05 E7, forbids fulfilling it. Signed requests, and requests from a
service provider whose metadata omits the flag or sets it to false, are
received as before. `RequireSigned`, Compatibility, and raw identity providers
built without an `IdpConfig` are unchanged.

`SpMetadata::is_authn_request_signed` now returns true when any SAML 2.0
`SPSSODescriptor` of the entity sets the flag. Before, an entity with two such
roles read false. A raw service provider built from that metadata now signs
its AuthnRequests.

**Upgrade:** ask the service provider to sign its requests, or to publish
metadata without `AuthnRequestsSigned="true"`, then import that metadata
again.

### 3.1 Send the identity provider's entity ID as the Response `Issuer`

**Affects:** identity providers that write a Response `Issuer` other than the
entity ID in their metadata. For raw `flow`, this applies with `from_issuer`.

**Before:** on a successful response only the assertion `Issuer` was
compared. **Now:** the Response `Issuer` gets the check that an error response
already got.

| Successful response | Before | Now |
| --- | --- | --- |
| Response `Issuer` is not the identity provider | Accepted | `IssuerMismatch` with that issuer |
| More than one Response `Issuer` | Accepted | `IssuerMismatch` without an issuer |
| No Response `Issuer` | Accepted | Accepted |

A response with a verified Response signature changes only when the identity
provider signed another `Issuer` itself.

**Upgrade:** correct the identity provider's issuer, or build the
`IdpDescriptor` for the entity ID it sends.

### 3.2 Handle correlation errors on an SSO error response

**Affects:** code that matches `StatusNotSuccess` to show a login failure from
the identity provider.

**Before:** the status came first. **Now:** a `Response` with a status other
than `Success` returns `SamlError::StatusNotSuccess` only after a present
signature verifies and its `Issuer`, `InResponseTo`, and `Destination` checks
pass. The response still does not need a signature, and a missing `Issuer` is
accepted.

| Error response | Before | Now |
| --- | --- | --- |
| Present signature does not verify | `StatusNotSuccess` | `SignatureVerification` |
| Wrong `Issuer` | `StatusNotSuccess` | `IssuerMismatch` |
| Wrong or missing `InResponseTo` | `StatusNotSuccess` | `InResponseToMismatch` |
| Wrong `Destination`, or signed without one | `StatusNotSuccess` | `DestinationMismatch` |

**Upgrade:** treat these errors as a failed login too. `StatusNotSuccess` now
means the response came for this login and this service provider. Without a
signature it is still not proof of who sent it.

### 3.3 Expect a future bearer `NotBefore` to be rejected

**Affects:** service providers whose identity provider sends a bearer
`SubjectConfirmationData@NotBefore`.

**Before:** the attribute was ignored. **Now:** it is checked when present.

- A `NotBefore` later than now plus the `NotBefore` clock skew, or one that
  cannot be read as a timestamp, no longer confirms the assertion. When no
  other bearer confirmation is satisfied, the response fails with
  `SamlError::SubjectConfirmationInvalid` and
  `SubjectConfirmationReason::TimeWindowInvalid`.
- A namespace-qualified `NotBefore` attribute on `SubjectConfirmationData`
  returns `SamlError::ProtocolProfile`, as qualified copies of the other
  attributes the library reads already do.
- A `NotBefore` that has been reached is still accepted.

**Upgrade:** synchronize the clocks, or widen
`ClockSkew::with_not_before_millis`.

### 3.4 Reject an empty `InResponseTo` on typed unsolicited SSO

**Affects:** `accept_unsolicited_sso` and
`accept_unsolicited_sso_with_outstanding_logout`.

**Before:** an empty attribute was read as absent and the response was
accepted. **Now:** a `Response` or bearer `SubjectConfirmationData` with
`InResponseTo=""` returns `SamlError::InResponseToMismatch` with
`expected: None` and `actual: Some("")`.

**Upgrade:** ask the identity provider to omit the attribute. Until it does,
the raw `parse_unsolicited_login_response` still reads an empty value as
absent. saml-rs identity providers stopped writing it
([section 4.5](#45-expect-unsolicited-responses-without-inresponseto)).

### 3.5 Supply a published ACS to `accept_unsolicited_sso`

**Affects:** callers that pass `SamlValidationContext::with_recipient_endpoint`
to `accept_unsolicited_sso` or `accept_unsolicited_sso_with_outstanding_logout`.
See [Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md).

**Before:** the URL was ignored, and the response had to name the default
assertion consumer for its binding. **Now:** an unsolicited response's
`Destination` and bearer `Recipient` are compared with the supplied URL. A
response sent to another assertion consumer you publish is accepted when you
supply that consumer's URL.

- A supplied URL that your metadata does not publish as an
  `AssertionConsumerService` for the incoming binding returns
  `SamlError::Invalid`.
- A response that names another assertion consumer than the supplied one
  returns `SamlError::DestinationMismatch`.

**Upgrade:** pass the URL of the endpoint that received the request, taken
from your HTTP routing, or leave it unset to compare with the default
assertion consumer.

### 3.6 Read each attribute by `Name` and `NameFormat`

**Affects:** code that reads `SsoSession::attributes`, the raw
`attributeNameFormats` extract, or builds a `FlowResult` and converts it to
`SsoSession`.

**Before:** `<Attribute>` elements with the same `Name` and different
`NameFormat` were one entry with the `NameFormat` of the first element and the
values of all of them. The values of a repeated element after the first were
dropped when that element had more than one value.
**Now:** they are separate `Attribute` entries, as Errata 05 E49 identifies an
attribute by both. An omitted `NameFormat` and `unspecified` are still one
attribute. Every value of repeated elements with the same `Name` and
`NameFormat` is kept.

`Attributes::get` returns the first entry with a name. If an identity provider
sends one name in more than one format, look it up by both:

```rust
let role = session.attributes().as_slice().iter().find(|attribute| {
	attribute.name() == "role" && attribute.format() == Some(&AttributeNameFormat::Uri)
});
```

Raw extracts:

- Each `attributeNameFormats` entry of `FlowResult::extract` now has an
  `attributeValue` array with the element's values. Allow the new key when you
  compare or iterate over those entries.
- A hand-built `FlowResult` converted to `SsoSession` needs an
  `attributeNameFormats` entry per `<Attribute>`, with `name`, `nameFormat`
  when it has one, and `attributeValue`. The typed attributes come from those
  entries. An extract with `attributes` and no `attributeNameFormats`, or an
  entry without `attributeValue`, returns `SamlError::Invalid`.

### 3.7 Stop relying on the signing-flag conflict when the IdP does not require signing

**Affects:** a service provider that signs AuthnRequests, through
`AuthnRequestSigningPolicy::Sign` or `AuthnRequestsSigned="true"` in its raw
metadata, and calls `start_sso` or `create_login_request` for an identity
provider whose `WantAuthnRequestsSigned` is false or omitted. See
[Web Browser SSO generation](../conformance/web-browser-sso-generation.md#service-provider-authnrequest).

**Before:** the call returned `SamlError::Invalid` with
`ERR_METADATA_CONFLICT_REQUEST_SIGNED_FLAG` and built no request.
**Now:** it returns a signed request. A service provider that does not sign
still gets that error when the identity provider's `WantAuthnRequestsSigned`
is true.

**Upgrade:** remove handling written for the signing case. A service provider
that should send unsigned requests leaves `AuthnRequestSigningPolicy::Sign`
unset.

### 3.8 Read the RelayState a peer adds to a response

**Affects:** `finish_sso`, `finish_slo`, and
`finish_name_id_management_redirect`. See
[Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md),
[Single Logout rules](../conformance/single-logout.md), and
[name identifier management](../conformance/name-id-management.md).

**Before:** when the request carried no RelayState, a response with one
returned `SamlError::RelayStateMismatch`.
**Now:** that response is accepted, empty or not, as Bindings §3.4.3 and
§3.5.3 let the responder add one. A response that changes, empties, or drops a
RelayState the request carried still returns that error.

The received value is reported by `SsoSession::relay_state`,
`LogoutCompleted::relay_state`, and the return value of
`finish_name_id_management_redirect`
([section 1.9](#19-bind-the-relaystate-from-finish_name_id_management_redirect)).

**Upgrade:** if you sent no RelayState and treat its absence as part of your
state, inspect the reported value before you act on it. Treat it as untrusted
input, and sanitize a URL taken from it before you redirect.

### 3.9 Expect an unevaluated bearer `NotOnOrAfter` to pass replay storage

**Affects:** `finish_sso` or `accept_unsolicited_sso` under
`ReplayPolicy::RequireCache`, and direct calls to
`SsoSession::check_and_store_replay`. See
[metadata and replay](../conformance/metadata-and-replay.md#replay).

**Before:** a bearer confirmation whose `NotOnOrAfter` did not parse returned
`SamlError::TimeWindowInvalid` with `TimeWindowField::ReplayExpiration` after
every other check had passed, while the same response was accepted under
`DisabledForCompatibility`.
**Now:** the session assertion gets its replay deadline by the rule the other
assertions already used: the latest bearer
`SubjectConfirmationData@NotOnOrAfter` that parses as an instant. A
confirmation whose value does not parse is ignored when another one parses.
A response with one bearer confirmation is not affected.

**Upgrade:** none. Such a response is now accepted, and its identifiers are
stored.

### 4.1 Issue a subject without confirmations

**Affects:** identity providers that pass a `Subject` with
`SubjectConfirmation` values to a login response method.

**Before:** the confirmations were dropped and only the library's bearer

reached the service provider.
**Now:** such a subject returns `SamlError::Unsupported`.

**Upgrade:** build the subject with no confirmations. The response is the one
0.7 sent:

```rust
use saml_rs::{NameId, Subject};

let subject = Subject::new(NameId::new("alice@example.com", None), Vec::new());
```

A proxy that re-issues the subject of an accepted login is affected too,
because that subject carries the upstream bearer confirmation. Keep its

let subject = Subject::new(session.subject().name_id().clone(), Vec::new());

### 4.2 State the authentication context an exact request asks for

**Affects:** `respond_sso` with `apply_web_browser_sso_generation_rules`,
`respond_sso_artifact` under those rules, and `respond_paos_sso`. See
[generation rules](../conformance/web-browser-sso-generation.md#identity-provider-response).

**Before:** the request's `RequestedAuthnContext` was ignored, and the
response claimed the unspecified class.
**Now:** the typed `AuthnRequest` reads it. When its `Comparison` is `exact`
or omitted, a success response returns `SamlError::Invalid` unless the
authentication context it writes is one of the requested references. Requests
with another comparison, or without `RequestedAuthnContext`, are answered as
before.

**Upgrade:** read `AuthnRequest::requested_authn_context`, then pass the
context the subject was authenticated with:

```rust
let options = RespondSso::post()
    .apply_web_browser_sso_generation_rules()
    .authn_context(AuthnContextReference::class(
        "urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport",
    )?);
```

or, when no requested context can be met, answer with an error status:

```rust
let options = RespondSso::post()
    .status(Status::responder().with_subordinate(SubordinateStatusCode::no_authn_context()));
```

For PAOS, use `RespondPaosSso::authn_context`, or `reject_paos_sso` with the
same status. `RespondSso::authn_context` without
`apply_web_browser_sso_generation_rules` returns `SamlError::Invalid`, because
that response has no `AuthnStatement`.

**Received requests:** `receive_sso` and `receive_paos_sso` now return
`SamlError::Invalid` for a `RequestedAuthnContext` outside its schema: a
`Comparison` other than `exact`, `minimum`, `maximum`, or `better`, no
references, both class and declaration references, or a second
`RequestedAuthnContext`. A namespace-qualified `Comparison`, or a reference in
another namespace, returns `SamlError::ProtocolProfile`; those two also apply
to raw request parsing (`flow`, `parse_login_request`). Before, the element
was not read.

**Raw extract:** `authnContextClassRef` now holds the class references inside
`RequestedAuthnContext`. Before, it read a path that a valid request never
has, and was empty. `requestedAuthnContext`,
`requestedAuthnContextComparison`, and `authnContextDeclRef` are new keys.

### 4.3 Read and issue the requested `SPNameQualifier`

**Affects:** identity providers that receive an `AuthnRequest`, and that issue
a `NameId` through a login response method.

**Received policy.** `AuthnRequest::name_id_policy` after `receive_sso` or
`receive_paos_sso` keeps `SPNameQualifier`, returned by
`NameIdPolicy::sp_name_qualifier`. A `NameIDPolicy` with only
`SPNameQualifier` is now `Some`. Before, it was `None`, as if the request had
no policy. A namespace-qualified `SPNameQualifier` returns
`SamlError::ProtocolProfile` from `receive_sso`, `receive_paos_sso`, and raw
request parsing (`flow`, `parse_login_request`). Before, it was ignored. The
raw `nameIDPolicy` extract carries a `spNameQualifier` key when the attribute
is present.

**Issued `NameID`.** The issued `<NameID>` now carries the `NameQualifier` and
`SPNameQualifier` of the `NameId`. Before, both were dropped. The service
provider reads them back from `SsoSession::name_id`. If you set them only for
your own records, build the `NameId` with `NameId::new` or pass `None` for
them.

**Requested namespace.** A success response to an `AuthnRequest` whose
`NameIDPolicy` has an `SPNameQualifier` and a SAML-defined `Format` other than
`unspecified` or `encrypted` returns `SamlError::Invalid` unless the `NameId`
has that same `SPNameQualifier`. This applies under
`RespondSso::apply_web_browser_sso_generation_rules` and always in
`respond_paos_sso`. Errata 05 E15 requires the two values to be identical.

**Upgrade:** issue an identifier in the requested namespace with that
qualifier, or answer with an error status:

```rust
use saml_rs::constants::status_code;

let requested = received
    .message()
    .name_id_policy()
    .and_then(NameIdPolicy::sp_name_qualifier);
let options = match requested {
    Some(namespace) if !serves_namespace(namespace) => RespondSso::post()
        .apply_web_browser_sso_generation_rules()
        .status(Status::responder().with_subordinate(
            SubordinateStatusCode::try_new(status_code::INVALID_NAME_ID_POLICY)?,
        )),
    Some(_) | None => RespondSso::post().apply_web_browser_sso_generation_rules(),
};
let name_id = NameId::with_qualifiers(
    stored_persistent_value,
    Some(NameIdFormat::Persistent),
    None,
    requested.map(str::to_string),
    None,
);
```

A `NameId` with `NameQualifier` or `SPNameQualifier` and a login response
template returns `SamlError::Invalid`, as `SPProvidedID` already did. Before,
the template dropped them.

### 4.4 Issue the requested subject

**Affects:** identity providers that answer an `AuthnRequest` carrying a
`<Subject>` through `respond_sso` or `respond_sso_artifact` with
`RespondSso::apply_web_browser_sso_generation_rules`, or through
`respond_paos_sso`. See
[Web Browser SSO generation](../conformance/web-browser-sso-generation.md#identity-provider-response).

**Before:** the library issued any subject.
**Now:** a success response returns `SamlError::Invalid` unless the issued
`NameId` has the value, `Format`, `NameQualifier`, `SPNameQualifier`, and
`SPProvidedID` of the requested `<NameID>`. An omitted `Format` counts as
`unspecified`. A `NameId` in the `NameIDPolicy` `Format`, when that differs
from the requested format, is still issued.

- A requested `<BaseID>` has no success response. Core §3.4.1.4 as amended by
  Errata 05 E75, and Profiles §4.1.4.1, require an error status for an
  unmatched requested subject.
- As library policy, a requested `<EncryptedID>` that was not decrypted has no
  success response either, because the library cannot show the match.

**Upgrade:** issue the requested `NameId` when the authenticated principal is
that subject. Otherwise answer with an error status:

```rust
use saml_rs::constants::status_code;

let identifier = received
    .message()
    .requested_subject()
    .map(RequestedSubject::identifier);
let options = RespondSso::post().apply_web_browser_sso_generation_rules();
let options = match identifier {
    Some(RequestedSubjectIdentifier::NameId(requested)) if !authenticated_as(requested) => options
        .status(Status::responder().with_subordinate(
            SubordinateStatusCode::try_new(status_code::UNKNOWN_PRINCIPAL)?,
        )),
    Some(RequestedSubjectIdentifier::BaseId | RequestedSubjectIdentifier::EncryptedId) => {
        options.status(Status::responder())
    }
    Some(RequestedSubjectIdentifier::NameId(_) | RequestedSubjectIdentifier::NoIdentifier)
    | None => options,
};
```

Answer `respond_paos_sso` the same way with `reject_paos_sso`.

### 4.5 Expect unsolicited responses without `InResponseTo`

**Affects:** identity providers that send unsolicited login responses through
`initiate_sso`, `initiate_sso_artifact`, or the raw `create_login_response`
without `in_response_to`, and login response templates that contain
`InResponseTo="{InResponseTo}"`.

**Before:** samlify-port generation and templates wrote `InResponseTo=""`,
which the schema does not allow.
**Now:** an unsolicited response omits `InResponseTo` on the `Response` and on
the bearer `SubjectConfirmationData`. An `in_response_to` of `Some("")` is
treated as no request. A template element whose text is only `{InResponseTo}`
is removed when there is no request, as `{NameIDFormat}` already is.
Solicited responses are unchanged.

**Upgrade:** update a peer service provider or a test that matched the empty
attribute to expect no `InResponseTo`.

### 4.6 Give each attribute an absolute `NameFormat`

**Affects:** identity providers that send attributes through
`RespondSso::attributes` or `RespondPaosSso::attributes`.

**Before:** any `NameFormat` was written. **Now:** a `NameFormat` that is
blank or not an absolute URI reference, such as `not a uri` or
`/relative/path`, returns `SamlError::Invalid`. Core §1.3.2 requires an
absolute URI.

**Upgrade:** use an `AttributeNameFormat` variant, a deployment URI such as
`https://example.com/attribute-name-format`, or `None` to omit `NameFormat`.

### 4.7 Expect padded persistent and transient formats to be checked

**Affects:** a `NameId` you send, or a NameID format you configure, that is a
`NameIdFormat::Custom` URI naming the persistent or transient format with
surrounding whitespace. Other formats are not affected.

**Now:** the format is compared after the `xs:anyURI` whitespace collapse, as
it already was for the absolute URI check.

| Padded format | Calls | Result now |
| --- | --- | --- |
| Transient | `start_name_id_management`, `start_name_id_management_redirect` | `SamlError::ProtocolProfile` |
| Persistent or transient, value longer than 256 characters | Those two, every login response method, and the raw login response | `SamlError::Invalid` |
| Persistent without qualifiers | `ManageNameIDRequest` generation | Carries the default `NameQualifier` and `SPNameQualifier` |

**Upgrade:** use `NameIdFormat::Persistent` or `NameIdFormat::Transient` to
write the format without padding.

### 4.8 Choose valid, distinct tag prefixes

**Affects:** `tag_prefix_protocol` or `tag_prefix_assertion` set on
`EntitySetting` or `TemplatePolicy`.

**Before:** a prefix such as `1a`, `a,b`, `-x`, `xml`, or `xmlns` was accepted
and produced XML that does not parse, or failed later with another error.
**Now:** each prefix must be an XML NCName other than `xml` and `xmlns`, and
the two must differ. Otherwise generating a login response, a logout request
or response, or a NameID management message returns `SamlError::Invalid`.

A custom login response, logout request, or logout response template is now
rewritten in one pass. With `tag_prefix_protocol = "saml"`, the template's
`samlp:` elements take `saml:`. Before, they were rewritten again to
`tag_prefix_assertion`, and the root declared that prefix twice.

**Upgrade:** pick a prefix that starts with a letter or `_` and contains only
letters, digits, `_`, `-`, or `.`.

### 4.9 Fill attribute names before building the login response template

**Affects:** a `LoginResponseAttribute` field of a login response template that
contains `{`, and direct calls to `attribute_statement_builder`.

**Before:** a `Name` of `role{NameFormat}` or `{NameID}` was filled from
another placeholder, and a `custom` callback could fill its own `{Tenant}`
inside a `Name`.
**Now:** the `Name`, `NameFormat`, `xsi:type`, `xmlns:xs`, and `xmlns:xsi`
text is issued as configured. Each `{` is written as `&#123;`, so no
placeholder pass fills it. Fields without `{` produce the same XML.

**Upgrade:** put the final text in the `LoginResponseAttribute` before you
create the response.

no `unsignedShort` index is left.

**Upgrade:** set a different index with `AcsEndpoint::with_index`, or
`Endpoint::index` on raw configuration, or leave one unset.

### 5.2 Check the index of an ACS without one

**Before:** when an explicit index on another ACS already used the position of
an ACS without an index, both were written with the same index.
**Now:** an ACS without an explicit index is still written with its position
in the list, unless another ACS uses that position. Then it gets the smallest
index no other ACS uses. Metadata that already had unique indexes is written
unchanged.

**Upgrade:** if you published metadata with a duplicate index, check which
index each ACS has now. Update peers or stored
`AssertionConsumerServiceIndex` values that expected the old one. To keep an
index stable, set it explicitly.

### 5.3 Stop relying on `isDefault` outside ACS

**Before:** `Endpoint::is_default` wrote `isDefault` on every endpoint.
**Now:** it writes `isDefault` on `AssertionConsumerService` only.
`SingleSignOnService`, `SingleLogoutService`, and `ManageNameIDService` no
longer carry it, because the metadata schema does not define it on them.

**Upgrade:** if a peer read the flag on one of them, tell it which endpoint to
use.

### 5.4 Use a URI of at most 1024 characters as your entity ID

**Affects:** `SpConfig`, `IdpConfig`, `Saml::sp`, `Saml::idp`,
`EntityId::try_new`, `EntityId::from_str`, `EntityId::try_from`,
`generate_sp_metadata`, `generate_idp_metadata`, `try_generate_idp_metadata`,
`ServiceProvider::from_config`, and `IdentityProvider::from_config`. See
[entity identifiers](../conformance/identifiers.md#entity-identifiers).

**Before:** any value with a non-whitespace character was accepted, and raw
metadata generation also accepted an empty `entity_id`, which is what
`SpMetadataConfig::default()` and `IdpMetadataConfig::default()` hold.
**Now:** these return `SamlError::Invalid` when the entity ID is not an
absolute URI reference, is longer than 1024 characters, or has leading or
trailing whitespace, a tab, a line break, or consecutive spaces.

**Upgrade:** give your own service provider or identity provider an absolute
URI, such as `https://sp.example.com/metadata` or `urn:example:sp`, and trim
whitespace from a value you read from configuration. Changing it changes the
`entityID` and `Issuer` your peers see, so register the new value with them.
In raw `SpMetadataConfig` and `IdpMetadataConfig`, set `entity_id`
explicitly.

A peer's entity ID is not affected. Imported metadata and received `Issuer`
values are read as before. To name a peer whose entity ID is not a URI, such as
the expected entity ID passed to `IdpDescriptor::from_metadata_xml_for`, use
`EntityId::new`.

### 5.5 Refresh peer metadata before its `validUntil`

**Affects:** peer metadata imported into `IdpDescriptor` or `SpDescriptor`
that carries `validUntil`. Metadata without `validUntil` is not affected, and
an elapsed `cacheDuration` does not make metadata unusable. See
[metadata rules](../conformance/metadata-and-replay.md).

**Before:** the attribute was ignored and expired metadata stayed in use.
**Now:** every typed flow refuses a descriptor once the earliest `validUntil`
of the peer's role descriptor, its `EntityDescriptor`, and any enclosing
`EntitiesDescriptor` has been reached. It returns
`SamlError::TimeWindowInvalid` with `TimeWindowField::MetadataValidUntil`.
Flows that take a `SamlValidationContext` compare with its clock. The others,
such as `start_sso`, `respond_sso`, and `start_slo`, compare with the system
clock.

Import returns the same error when a `validUntil` is not an `xs:dateTime` with
a timezone, such as `2030-01-01T00:00:00` without `Z`. As library policy, it
also rejects hour 24 (`2030-01-01T24:00:00Z`), a leap second other than
23:59:60 UTC on the last day of a month, and a year outside 0001 through 9999,
although XML Schema allows them.

**Upgrade:** fetch fresh metadata from the publisher and import it again. Ask a
peer that publishes a value without a timezone, or one of those values, to
publish a UTC instant such as `2030-01-01T00:00:00Z`.

### 5.6 List SAML 2.0 on the peer's role descriptor

**Affects:** peer metadata imported with `IdpDescriptor` or `SpDescriptor`, or
parsed with `IdpMetadata`, `SpMetadata`, `IdentityProvider::from_metadata`, or
`ServiceProvider::from_metadata`. `Metadata::parse` is unchanged. See
[metadata trust](../conformance/metadata-and-replay.md#metadata-trust).

**Before:** every element named `IDPSSODescriptor` or `SPSSODescriptor` was
read. **Now:** only one in the `urn:oasis:names:tc:SAML:2.0:metadata`
namespace whose `protocolSupportEnumeration` lists
`urn:oasis:names:tc:SAML:2.0:protocol` is read.

- Metadata with no such role returns
  `SamlError::MissingMetadata("IDPSSODescriptor")` or
  `SamlError::MissingMetadata("SPSSODescriptor")`. Before, a role that listed
  only SAML 1.1, or a role element outside the metadata namespace, was accepted
  as the SAML 2.0 peer.
- Keys, `WantAuthnRequestsSigned`, `AuthnRequestsSigned`,
  `WantAssertionsSigned`, `NameIDFormat`, endpoints, and `validUntil` of a role
  for another protocol are ignored. Before, its certificates verified SAML 2.0
  messages, and its flags and endpoints were used when it came first. A message
  signed only with such a role's key now fails signature verification.
- With a second `SPSSODescriptor` for another protocol, `AuthnRequestsSigned`
  and `WantAssertionsSigned` were read as false. They are now read from the
  SAML 2.0 role. For a service provider whose SAML 2.0 role sets
  `WantAssertionsSigned`, an identity provider now signs the assertion, and
  over HTTP-POST signs the `Response` only when `want_message_signed` is set.
- `get_name_id_format` returns only the formats of the role read. Before, it
  also returned the formats of the entity's other SSO roles.
  `IdentityProvider::from_metadata` and `ServiceProvider::from_metadata` copy
  that list into `EntitySetting::name_id_format` when it is not empty, and
  otherwise keep the `name_id_format` you pass.
- A raw entity built from its own metadata with both an `IDPSSODescriptor` and
  an `SPSSODescriptor`, such as a proxy, now writes the first format of its own
  role wherever it writes its first configured NameID format: an issued
  `NameID`, an AuthnRequest `NameIDPolicy`, and a LogoutRequest or
  ManageNameIDRequest `NameID` without a format. Before, it wrote the first
  `NameIDFormat` of the entity, whichever role it was in. To keep a format,
  list it first in the `NameIDFormat` elements of that role.

**Upgrade:** ask the peer to list `urn:oasis:names:tc:SAML:2.0:protocol` in the
`protocolSupportEnumeration` of its SAML 2.0 role and to publish its role
elements in the metadata namespace. An element written without a prefix needs
`xmlns="urn:oasis:names:tc:SAML:2.0:metadata"` on it or on an ancestor:

```xml
<EntityDescriptor xmlns="urn:oasis:names:tc:SAML:2.0:metadata" entityID="https://idp.example.com">
  <IDPSSODescriptor protocolSupportEnumeration="urn:oasis:names:tc:SAML:2.0:protocol">
    ...
  </IDPSSODescriptor>
</EntityDescriptor>
```

### 5.7 Expect padded endpoint attributes in peer metadata to be read

**Affects:** metadata parsed with `IdpMetadata`, `SpMetadata`,
`IdpDescriptor`, `SpDescriptor`, `IdentityProvider::from_metadata`, or
`ServiceProvider::from_metadata` that writes leading, trailing, or repeated
whitespace in an endpoint attribute. See
[metadata trust](../conformance/metadata-and-replay.md#metadata-trust).

**Now:** `SingleSignOnService`, `ArtifactResolutionService`, and
`ManageNameIDService` collapse whitespace in `Binding`, `Location`,
`ResponseLocation`, and `index`, as `SingleLogoutService` and
`AssertionConsumerService` already did.

| Peer metadata | Before | Now |
| --- | --- | --- |
| Padded `Binding` on `SingleSignOnService` | `get_single_sign_on_service` returned `None` | Endpoint returned, trimmed |
| Padded `Location` on these three endpoints | Untrimmed URL returned and used | Trimmed URL returned, sent to, and matched against a received `Destination` |
| `ArtifactResolutionService` `index` with surrounding whitespace | `SamlError::Invalid` | Read as its number |
| `ArtifactResolutionService` whose `Binding` or `Location` is only whitespace | Whitespace returned | `SamlError::Invalid`, as for an empty value |
| `SingleSignOnService` or `ManageNameIDService` whose `Location` is only whitespace | Whitespace returned as the URL | Skipped for requests. A `ManageNameIDService` response still goes to a non-empty `ResponseLocation` |
| Namespace-qualified attribute such as `x:Location` | Read by its local name | Not read. An `ArtifactResolutionService` with only the qualified attribute returns `SamlError::Invalid`; the other two are skipped |

**Upgrade:** compare a returned endpoint with the trimmed string. Ask a peer
whose endpoints use a whitespace-only or qualified `Binding` or `Location` to
publish the unqualified attribute with its URI.

### 6.1 Compare the received NameID with its attributes

**Affects:** code that reads a typed `LogoutRequest` NameID.

**Before:** `LogoutRequest::name_id` returned the value with no attributes.
**Now:** it returns the `Format`, `NameQualifier`, `SPNameQualifier`, and
`SPProvidedID` of the received `<NameID>`.

- A comparison with `==` includes every attribute, so a stored `NameId`
  without the attributes the peer sends no longer compares equal. Store the
  `NameId` from the accepted assertion, which carries the same attributes, or
  compare `NameId::value` when your session lookup is by value only.
- An `OutstandingLogout` built from the received `NameId` carries its
  `Format`. A later assertion matches only when it has the same `Format`, as
  Core §3.3.4 strong matching requires. Before, a value match was enough. An
  `unspecified` `Format` still compares values only, because an omitted
  `Format` means `unspecified` (Core §2.2.2).

### 6.2 Add the status to a hand-built `FlowResult`

**Affects:** code that builds a typed `LogoutResponse` from a `FlowResult` it
assembled itself. A `FlowResult` returned by the raw logout parsers already
carries these fields. `LogoutResponse::status` is a compatible addition.

**Now:** `LogoutResponse::try_from(FlowResult)` reads the top-level status code
from the extract. It returns `SamlError::ProtocolProfile` when `statusCode` is
missing, or is not `Success`, `Requester`, `Responder`, or `VersionMismatch`.

**Upgrade:** add the top-level code, and the subordinate code when the response
has one:

```rust
use saml_rs::constants::status_code;
use saml_rs::util::Value;

let status_fields = [
	("statusCode".to_string(), Value::Str(status_code::SUCCESS.to_string())),
	(
		"subordinateStatusCode".to_string(),
		Value::Str(status_code::PARTIAL_LOGOUT.to_string()),
	),
];
```

### 6.3 Accept a logout response over another front-channel binding

**Affects:** `finish_slo`. See
[Single Logout rules](../conformance/single-logout.md).

**Before:** a response over a different binding than the request returned
`SamlError::UnsupportedBinding`.
**Now:** a response to an HTTP-Redirect, HTTP-POST, or HTTP-POST-SimpleSign
request is accepted over any of those three bindings, as Profiles §4.4.3.4 and
§4.4.3.5 allow. The `Destination` is checked against your
`SingleLogoutService` for the binding the response arrived on. A response over
a front-channel binding your metadata does not publish returns
`SamlError::MissingMetadata`. A SOAP response to a front-channel request, or a
front-channel response to a SOAP request, still returns
`SamlError::UnsupportedBinding`.

**Upgrade:** if you relied on that error to refuse a binding, stop publishing a
`SingleLogoutService` for it.

### 6.4 Answer a logout request whose `EncryptedID` does not decrypt

**Affects:** `receive_slo` with a `decryption_key` configured. See
[encrypted principal identifier](../conformance/single-logout.md#encrypted-principal-identifier).

**Before:** an authenticated `LogoutRequest` whose `EncryptedID` no
configured key decrypts returned the decryption error, for example
`SamlError::Crypto` for a key that does not match or an unsupported algorithm,
or `SamlError::Unsupported` for RSA-v1.5 key transport that is not allowed.
**Now:** it returns `Ok` with a `Received<LogoutRequest>` whose `name_id()` is
`None`, as it already did with no decryption key. The `SessionIndex` values
are still returned. A decryption key that does not load, an `EncryptedID`
without exactly one `EncryptedData`, and plaintext that is not one `NameID`
still return an error.

**Upgrade:** check `name_id()` before you invalidate sessions. To report the
unknown principal, answer with an error status:

```rust
use saml_rs::{RespondSlo, Status, SubordinateStatusCode};

let options = RespondSlo::post()
    .status(Status::requester().with_subordinate(SubordinateStatusCode::unknown_principal()));
```

### 6.5 Order the children of a `ManageNameIDRequest`

**Affects:** identity providers that call `receive_name_id_management`, and
either role calling `receive_name_id_management_redirect`.

**Before:** `Issuer`, `ds:Signature`, and `Extensions` were skipped wherever
they appeared.
**Now:** a received `ManageNameIDRequest` must follow the protocol schema
sequence: at most one `Issuer`, one `ds:Signature`, and one `Extensions`, in
that order, then the identifier and the change. Another order, such as
`Extensions` after `Terminate` or before `Issuer`, or a second `Issuer`,
`Signature`, or `Extensions`, returns `SamlError::ProtocolProfile`.

**Upgrade:** ask a peer that sends another order to send the schema order.

### 6.6 Check custom subordinate status codes against the URI rule

**Affects:** your own URI passed to `SubordinateStatusCode::try_new`, and a
custom `LogoutResponse` template that writes `Consent`, a `StatusCode`
`Value`, or the `Issuer`.

**Before:** these values were parsed as WHATWG URLs.
**Now:** they are read as an absolute URI reference by the rule a NameID
`Format` already follows: RFC 2396 with RFC 2732 IPv6 hosts, after the
`xs:anyURI` escaping of XML Schema 1.0. `try_new` still rejects whitespace and
`&`, `"`, `'`, `<`, and `>`, and the outbound check still rejects whitespace.
`Destination` is still parsed as a URL.

`try_new` now returns `SamlError::Invalid`, and `respond_slo` returns
`SamlError::ProtocolProfile` from its outbound check, for a value that:

- has nothing after the scheme, such as `urn:` or `mailto:`;
- has a `%` not followed by two hexadecimal digits, such as `urn:example:%zz`;
- has a second `#`, such as `urn:example:a#b#c`;
- has `[` or `]` in a path or at the start of an opaque part, such as
  `https://idp.example/a[b]` or `urn:[a]`;
- has a character XML 1.0 cannot carry, such as U+0001.

Before, these were accepted, and a non-XML character produced a message the
peer could not parse. A value with a host or port the URL parser refused, such
as an empty host, a non-numeric port, or a port above 65535
(`https://idp.example:70000/status`), is now accepted.

**Upgrade:** percent-encode the character as `%HH`, or use a URI such as
`urn:example:status:local-failure`.

### 7.1 Send well-formed, namespace-well-formed XML

**Affects:** every input `saml-rs` parses: received messages, metadata, SOAP and
PAOS envelopes, `saml_rs::context::is_valid_xml`, and
`saml_rs::xml::dom::parse`, `parse_with_limits`, `parse_roots`, and
`parse_roots_with_limits`. Well-formed input is not affected.

**Before:** the DOM accepted these inputs, and only the parser behind signature
verification and decryption rejected them.
**Now:** they return `SamlError::Xml`, as XML 1.0 and Namespaces in XML
require of a parser:

- an element still open at the end of the input, such as `<Root/><Second>`,
  including in `parse_roots`;
- `<` in an attribute value;
- a character outside the XML character range, written directly or as a
  character reference: a control character other than tab, line feed, and
  carriage return, U+FFFE, or U+FFFF;
- `--` inside a comment;
- a namespace prefix that the document does not declare;
- a binding of the `xmlns` prefix, a binding of `xml` to another namespace, or
  another prefix or the default namespace bound to the `xml` or `xmlns`
  namespace;
- two attributes on one element with the same namespace and local name;
- `]]>` in text;
- two attributes with no whitespace between them, such as `x="1"y="2"`;
- an element or attribute name that is not a qualified name: not an XML name,
  such as `1a`, with more than one colon, such as `a:b:c`, or with an empty
  prefix or local part, such as `a:`;
- an XML declaration that is not at the very start of the input, or a
  processing instruction whose target is `xml` in any letter case;
- an empty namespace name for a prefix, such as `xmlns:p=""`. An empty default
  namespace, `xmlns=""`, is still accepted.

A namespace name is compared after its character and entity references are
resolved, so `xmlns:b="&#x75;rn:a"` binds `urn:a`.

**Changed error variants:**

| Input | Before | Now |
| --- | --- | --- |
| Received message whose root, or a SAML element such as `<Assertion>`, uses an undeclared prefix | `SamlError::ProtocolProfile` | `SamlError::Xml`, before protocol-profile validation |
| More namespace bindings in scope than `XmlLimits::max_attributes_per_element` (64 by default) | `SamlError::Xml` from protocol-profile validation for messages; no limit for metadata | `SamlError::Invalid` with `ERR_XML_LIMIT_EXCEEDED` |

Update a `match` that expected the old variant. Raise
`max_attributes_per_element` if a metadata document you trust declares more.

`saml_rs::xml::extract` and `extract_with_limits` still accept one element cut
out of a larger document, such as an extracted `context` value, whose
prefixes are declared on an ancestor outside it. The other checks apply to it.

**Upgrade:** no option accepts the rejected input. Ask the peer to fix the XML
it sends.

### 7.2 Expect a line feed for each line break in received text

**Affects:** text that `saml-rs` reads from parsed XML: a `NameID`, an
attribute value, an `Issuer`, and every other element value in received
messages and metadata, including `saml_rs::xml::dom` and
`saml_rs::xml::extract` results.

**Before:** the carriage return was kept, so a peer that writes line breaks as
CRLF produced `"alice\r\nx"` where the signed value is `"alice\nx"`.
**Now:** a carriage return followed by a line feed, or a carriage return on its
own, written literally in text or in a CDATA section, reaches you as one line
feed, as XML 1.0 §2.11 requires. A carriage return written as `&#xD;` is still
a carriage return. XML attribute values, such as `Destination`, already worked
this way.

**Upgrade:** if you stored values received before the upgrade and compare them
with new ones, convert the stored values from peers that write literal line
breaks:

```rust
let stored = stored.replace("\r\n", "\n").replace('\r', "\n");
```

A value whose peer wrote the carriage return as `&#xD;` keeps it after the
upgrade, so do not convert those.

### 7.3 Size `XmlPolicy::limits` for SOAP envelopes and SimpleSign messages

**Affects:** deployments that set `XmlPolicy::limits` on the `Saml` instance
and receive SOAP through `answer_artifact_resolve`,
`ArtifactResolution::finish`, `receive_slo` or `finish_slo` with
`BrowserInput::soap`, `receive_name_id_management`, or
`StartedNameIdManagement::finish`, or receive HTTP-POST-SimpleSign messages.

**Before:** these inputs were read under `XmlLimits::default()`.
**Now:** the whole SOAP envelope, header included, and the decoded
SimpleSign message are read under the configured limits. A SOAP envelope over
a configured limit returns `SamlError::Invalid` with `ERR_XML_LIMIT_EXCEEDED`.
A SimpleSign message whose decoded size is over `max_bytes` returns
`SamlError::Invalid` with `ERR_BASE64_OUTPUT_LIMIT_EXCEEDED`. A limit above
the default now admits a larger input.

**Upgrade:** if you set limits below the defaults, check that they still fit
the largest envelope or SimpleSign message your peers send.
`SoapProtocolMessage::from_envelope` and the `TryFrom<BrowserInput>`
conversions to `HttpRequest` have no configuration and keep the defaults.

### 7.4 Send one SOAP `Header` before the `Body`

**Affects:** the calls in [section 7.3](#73-size-xmlpolicylimits-for-soap-envelopes-and-simplesign-messages)
that read SOAP, and `SoapProtocolMessage::from_envelope`. See
[SOAP envelope rules](../conformance/artifact-resolution.md).

**Now:** the SOAP envelope reader returns `SamlError::ProtocolProfile` when a
`Header` follows the `Body` or the envelope has more than one `Header`. An
envelope with two `Body` elements, one of them empty, returns
`SamlError::ProtocolProfile` instead of `SamlError::Xml`. The ECP reader
already refused these envelopes. SOAP 1.1 §4 requires a `Header` to be the
first child of `Envelope` and the `Body` to follow it.

**Upgrade:** ask a peer that sends another order to send a SOAP 1.1 envelope.

### 7.5 Expect signatures in SOAP messages to be verified where they sit

**Affects:** SAML messages received over SOAP: `receive_slo` and `finish_slo`,
`receive_name_id_management` and `StartedNameIdManagement::finish`,
`answer_artifact_resolve` and `ArtifactResolution::finish`, and
`receive_paos_sso`, `finish_paos_sso`, and
`finish_paos_sso_with_outstanding_logout`.

**Now:** the message read from a SOAP body declares every namespace in scope
from its ancestors, including the envelope's, and its signature is verified
against that element. Inclusive Canonical XML (`REC-xml-c14n-20010315`) takes
those declarations into the digest, so a verifier computes it as it would on
the message in place in the envelope.

| Message signed by the peer | Before | Now |
| --- | --- | --- |
| Alone, with exclusive canonicalization and no `InclusiveNamespaces` `PrefixList` naming an envelope prefix (saml-rs and most peers) | Accepted | Accepted |
| Alone, with Canonical XML, then wrapped in SOAP | Accepted | `SignatureVerification` with `SignatureVerificationReason::XmlSignature` |
| Alone, with exclusive canonicalization and a `PrefixList` naming a prefix the envelope declares | Accepted | `SignatureVerification` with `SignatureVerificationReason::XmlSignature` |
| With Canonical XML in place in the envelope | Rejected | Accepted |

The strings returned by `SoapProtocolMessage::xml()` and
`ResolvedProtocolMessage::xml()`, and a decrypted assertion, now carry these
inherited `xmlns` declarations, such as `xmlns:soap` from the envelope or the
`Response` namespaces on an assertion. Parse them as XML rather than comparing
them as text.

**Upgrade:** ask a peer that signs a standalone message with Canonical XML to
sign with exclusive canonicalization, as SAML Core §5.4.3 and §5.4.4
recommend, or to sign the message in place in the envelope.

### 7.6 Handle refused SOAP headers on PAOS logins

**Affects:** `receive_paos_sso`, `finish_paos_sso`, and
`finish_paos_sso_with_outstanding_logout`. See
[Enhanced Client/Proxy SSO](../conformance/enhanced-client-proxy.md).

| Envelope | Before | Now |
| --- | --- | --- |
| A header entry with `mustUnderstand="1"` or `"true"` that the receiver does not process | Ignored | `SamlError::Xml` |
| Not SOAP 1.1, a `Header` or `Body` outside the SOAP namespace, an `Envelope` child other than `Header` and `Body`, a missing `Body`, or an empty `Body` | `SamlError::ProtocolProfile` | `SamlError::Xml`, as the other SOAP readers already returned |

The service provider still accepts `ecp:RelayState` and `paos:Response`. The
identity provider accepts no `mustUnderstand` entry. `paos_soap_fault` answers
the identity provider error with a SOAP `Client` fault, as for any envelope
that is not a SAML request.

**Upgrade:** an enhanced client that sends such an entry must stop marking it
`mustUnderstand` or leave it out. If you branch on the variant, match both.

### 7.7 Remove Unicode whitespace before `base64_decode`

**Affects:** callers that pass base64 to `saml_rs::binding::base64_decode` or
`saml_rs::crypto::verify_message_signature`, and HTTP-Redirect and
HTTP-POST-SimpleSign reception of a `Signature` value.

**Before:** `base64_decode` skipped every Unicode whitespace character.
**Now:** it ignores the same whitespace as `base64_decode_with_limit`: space,
tab, line feed, form feed, and carriage return. Vertical tab, no-break space,
line separator, ideographic space, and every other Unicode whitespace character
return `SamlError::Base64`. Line-wrapped base64 still decodes.

**Upgrade:** if an integration must accept that input, remove the characters
before decoding:

```rust
let cleaned: String = input.split_whitespace().collect();
let bytes = saml_rs::binding::base64_decode(&cleaned)?;
```

### 7.8 Accept a received RelayState longer than 80 bytes

**Affects:** typed reception through `receive_sso`, `finish_sso`,
`accept_unsolicited_sso`, `receive_slo`, `finish_slo`,
`receive_name_id_management_redirect`, `finish_name_id_management_redirect`,
or `DeliveredArtifact::from_query` and `from_form`, and code that stores a
received RelayState. See
[Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md),
[HTTP-Artifact](../conformance/web-browser-sso-artifact.md),
[Single Logout rules](../conformance/single-logout.md), and
[name identifier management](../conformance/name-id-management.md).

**Before:** a received RelayState longer than 80 bytes returned
`SamlError::Invalid`, and responders could not echo one.
**Now:** it is accepted up to `MAX_RECEIVED_RELAY_STATE_BYTES` (4096 bytes).
Bindings §3.4.3, §3.5.3, and §3.6.3.1 limit the value the sender creates, not
what a receiver accepts. A longer value still returns `SamlError::Invalid`.
`respond_sso`, `respond_sso_artifact`, `respond_slo`, and
`respond_name_id_management_redirect` return a long received RelayState
unchanged, as Bindings §3.4.3 and §3.5.3 require.

A RelayState you create is still limited to 80 bytes. Passing a received long
value to `StartSso::relay_state`, `StartSlo::relay_state`,
`StartNameIdManagement::relay_state`, or `RespondSso::relay_state` returns
`SamlError::Invalid`. To answer a request with its own RelayState, leave
`RespondSso::relay_state` unset.

**Upgrade:** code that assumes every `RelayState` or `RelayStateParam` is at
most `MAX_RELAY_STATE_BYTES` must change. Check the length before you store a
received value in a column or cookie sized for 80 bytes.

### 7.9 Send one RelayState per message

**Affects:** typed reception over HTTP-POST or HTTP-Redirect with
`receive_sso`, `finish_sso`, `accept_unsolicited_sso`, `receive_slo`,
`finish_slo`, `receive_name_id_management_redirect`, or
`finish_name_id_management_redirect`. See
[Web Browser SSO acceptance](../conformance/web-browser-sso-acceptance.md),
[Single Logout rules](../conformance/single-logout.md), and
[name identifier management](../conformance/name-id-management.md).

**Before:** HTTP-POST and unsigned HTTP-Redirect used the first value and
ignored the others. An HTTP-Redirect query that repeated the exact name
`RelayState` returned `SamlError::Invalid("ambiguous Redirect field RelayState")`.
**Now:** a second `RelayState` form field or query parameter returns
`SamlError::Invalid("ambiguous form field")`. Names are compared after URL
decoding, so `RelayState=a&Rel%61yState=b` is a repeat. A repeated
`RelayState` was already refused on HTTP-POST-SimpleSign, on a signed
HTTP-Redirect, and on HTTP-Artifact. Bindings §3.4.3 and §3.5.3 define one
`RelayState` per message, so a conformant peer is not affected.

**Upgrade:** fix a peer or a proxy that adds a second `RelayState`, or remove
the extra field before you build the `BrowserInput`.

### 7.11 Check XML signature references and coverage

**Affects:** callers of `crypto::verify_signature`,
`crypto::verify_signature_with_limits`, `BergshamraBackend`, metadata signature
verification helpers, and flows that verify embedded XML signatures.

#### Keep processed references within the document

Every signature passed to the cryptographic verifier now takes the existing
same-document reference checks, including signatures inside extensions.
Previously, these checks covered only signatures directly under the root or
its direct Assertion children. All-signatures flows reject a processed external
reference with `SamlError::ReferenceResolution`, with reason
`ReferenceResolutionReason::ExternalReference`, before resolving references or
running transforms. Unsupported fragment forms keep
`ReferenceResolutionReason::UnsupportedReferenceUri`.

If your peer includes optional signatures with external references, remove
those signatures or change them to reference content within the message.
`AllowProviderSupportedForCompatibility` does not allow external references.
With `StrictRsaSha2`, every processed signature must also use only the existing
allowed reference transforms, even when that signature would fail verification
or cover unrelated content. Replace other transforms with enveloped-signature
and exclusive canonicalization transforms, or remove the optional signature.
The failure is `SamlError::AlgorithmUnsupported`.

The public `verify_signature` functions still process the first XML-DSig
signature in document order when a SAML candidate signature is present. They
preflight that actual first signature. They do not process later signatures.
Flows that inspect all signatures preflight all of them. Harmless optional
signatures that fail verification outside SAML candidate positions remain
ignorable when their processing passes these restrictions.

#### Consume the returned signed content

A successful public verification now always returns `(true, Some(xml))`.
For an assertion-bearing protocol response, `xml` remains the consumed signed
Assertion, and the existing checks still require coverage of every direct
Assertion. Other documents require coverage of the document root and return
that root. This includes status-only Responses, ArtifactResolve,
ManageNameIDRequest, and ArtifactResponse documents.

If you relied on `(true, None)`, handle `SamlError::SignedReferenceMismatch`
when a valid signature covers only a different object. Have the peer sign the
root of the document you need to authenticate. Root-covered documents that
previously returned no content now return their signed root.
`BergshamraBackend` applies the same guarantee before returning `Ok(())`.
Assertion-only signatures on SSO Response containers remain supported.

Flows that verify embedded signatures apply the same root-coverage rule.
Error and status-only Responses signed over another element now fail with
`SamlError::SignedReferenceMismatch` instead of reaching status handling.
For malformed successful Responses without Assertions, allow issuer-validation
errors as well as the previous empty-Assertion error when matching flow errors.

#### Verify metadata roots with metadata helpers

`crypto::verify_metadata_signature*` and `Metadata::verify_signature*` now
succeed only for a covered `EntityDescriptor` or `EntitiesDescriptor` root.
Previously, these helpers also accepted some signed non-metadata messages,
including LogoutRequest. Passing those roots now returns
`SamlError::SignedReferenceMismatch`. Pass a metadata descriptor to these
helpers. Use `crypto::verify_signature` for other signed XML documents.

These are library processing and coverage guarantees. They do not add general
schema or protocol validation to the public verification functions. The exact
standards scope and library policies are recorded in
[XML signature processing](../conformance/xml-signature-processing.md).

## 8. Smaller changes you may notice

These need no code change in a conformant deployment. Check them if you
compare outputs or match specific errors.

| Change | Before | Now |
| --- | --- | --- |
| `SsoSession::verified_xml_signatures` with a holder-of-key assertion before the bearer assertion | Reported the holder-of-key signature as `ConsumedAssertion` and dropped the bearer one | Reports the signature of the consumed bearer assertion. Acceptance is unchanged |
| A signed `Response` that mixes a plaintext `Assertion` and an `EncryptedAssertion` | `SamlError::Crypto` | Accepted when every assertion passes its checks. Under `RequireSigned` each plaintext assertion needs its own signature. A signature over the ciphertext is not reported as `ConsumedAssertion` evidence |
| A replayed or stale `LogoutRequest` or Redirect `ManageNameIDRequest` with an encrypted identifier | Could return the decryption error | Returns the replay, issuer, or age error before decrypting. `receive_slo` stores the request ID before decrypting |
| `ForceAuthn`, `IsPassive`, `AllowCreate`, and `AssertionConsumerServiceIndex` padded with XML whitespace in a received `AuthnRequest` | `SamlError::Invalid` | Read after trimming |
| A first `SingleSignOnService` or `SingleLogoutService` with an empty `Location` | `get_single_sign_on_service` and `get_single_logout_service` could return it | Skipped, so a later endpoint with a location is used, as the location lists already did. `get_support_bindings` omits a binding with no location |
| A Redirect or Artifact endpoint URL with a `#fragment`, or ending in `?` | Parameters went inside the fragment, or after `??` | Parameters join the query before the fragment |
| `SignatureConfig` with `Prepend` or `Append` on an empty element such as `<AuthnRequest/>` | Signature written outside the element | Signature written inside it. Refresh golden files of signed output |
| Bare certificate text with a non-ASCII character across a 64-byte boundary | Panic | `SamlError::Crypto` |
| A PAOS `AuthnRequest` without an assertion consumer URL or index | `SamlError::Invalid` | Answered at the service provider's default HTTP-POST or HTTP-POST-SimpleSign assertion consumer |
| A signature rejected by every trusted key, or two signatures that both fail a later check | The error came from the last metadata certificate | The error comes from the first rejection in key order, or the first signature in document order. The variant can differ |
| `respond_sso` or `respond_sso_artifact` for a request with no usable assertion consumer and a `Subject` with confirmations | `SamlError::Unsupported` | `SamlError::MissingMetadata("AssertionConsumerService")` |
| `Debug` of `IdpDescriptor` and `SpDescriptor` | Printed the metadata XML and parsed metadata | Prints the raw provider. Secrets stay redacted |

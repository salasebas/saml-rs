# How to upgrade from 0.7 to 0.8

Use this guide to upgrade `saml-rs`, `opensaml`, `samlify`, or `samlet` from
the latest `0.7.x` release to `0.8.x`. Apply only the sections that affect
your integration. The [changelog](../../CHANGELOG.md) lists compatible
additions.

## Give each ACS its own index

This and the next two sections apply if you generate service provider or
identity provider metadata through `Saml::sp`, `ServiceProvider::from_config`,
`IdentityProvider::from_config`, `generate_sp_metadata`, `generate_idp_metadata`,
or `try_generate_idp_metadata`. Metadata you import is not affected. See
[metadata rules](../conformance/metadata-and-replay.md).

Two `AssertionConsumerService` endpoints with the same explicit index now
return `SamlError::Invalid`. Before, the metadata published both, and looking
up that index failed. Set a different index with `AcsEndpoint::with_index`,
or `Endpoint::index` on raw configuration, or leave one unset.
More than 65,536 `AssertionConsumerService` endpoints now return
`SamlError::Invalid` too, because no `unsignedShort` index is left.

## Check the index of an ACS without one

An ACS without an explicit index is still written with its position in the
list. When an explicit index on another ACS already uses that position, the
ACS now gets the smallest index no other ACS uses. Before, both endpoints
were written with the same index.

Metadata that already had unique indexes is written unchanged. If you
published metadata with a duplicate index, check which index each ACS has
now. Update peers or stored `AssertionConsumerServiceIndex` values that
expected the old one. To keep an index stable, set it explicitly.

## Stop relying on `isDefault` outside ACS

`Endpoint::is_default` now writes `isDefault` on `AssertionConsumerService`
only. `SingleSignOnService`, `SingleLogoutService`, and `ManageNameIDService`
no longer carry it, because the metadata schema does not define it on them.
If a peer read the flag on one of them, tell it which endpoint to use.

## Remove Unicode whitespace before `base64_decode`

`base64_decode` now ignores the same whitespace as `base64_decode_with_limit`:
space, tab, line feed, form feed, and carriage return. Vertical tab, no-break
space, line separator, ideographic space, and every other Unicode whitespace
character now return `SamlError::Base64`. Line-wrapped base64 still decodes.

This affects callers that pass base64 containing those characters to
`saml_rs::binding::base64_decode` or `saml_rs::crypto::verify_message_signature`.
HTTP-Redirect and HTTP-POST-SimpleSign reception now reject a `Signature`
value that contains them.

If an integration must accept that input, remove the characters before
decoding:

```rust
let cleaned: String = input.split_whitespace().collect();
let bytes = saml_rs::binding::base64_decode(&cleaned)?;
```

## Pass `RespondPaosSso` to `respond_paos_sso`

This section applies when an identity provider answers Enhanced Client/Proxy
login with `Saml<Idp>::respond_paos_sso`. Service providers and `reject_paos_sso`
callers need no change.

`respond_paos_sso` takes a fourth argument, `RespondPaosSso`. Pass
`RespondPaosSso::default()` to keep the previous response, which has no
`AttributeStatement`:

```rust
let answered = idp.respond_paos_sso(&sp, &received, subject, RespondPaosSso::default())?;
```

To send attributes, set them on the options. They are written the same way as
`RespondSso::attributes`:

```rust
let answered = idp.respond_paos_sso(
	&sp,
	&received,
	subject,
	RespondPaosSso::default().attributes(attributes),
)?;
```

`respond_paos_sso` now returns `SamlError::Invalid` when these attributes are
combined with a login response template, or when a basic attribute name is not
an XML name.

## Compare the received NameID with its attributes

This and the next section apply if your integration reads a typed
`LogoutRequest` NameID, or builds a typed `LogoutResponse` from a `FlowResult`
you assembled yourself. `LogoutResponse::status` is a compatible addition.

`LogoutRequest::name_id` now returns the `Format`, `NameQualifier`,
`SPNameQualifier`, and `SPProvidedID` of the received `<NameID>`. Before, it
returned the value with no attributes.

Check code that compares the received `NameId` with a stored one using `==`.
The comparison now includes every attribute, so a stored `NameId` without the
attributes the peer sends no longer compares equal. Store the `NameId` from the
accepted assertion, which carries the same attributes, or compare
`NameId::value` when your session lookup is by value only.

An `OutstandingLogout` built from the received `NameId` now carries its
`Format`. A later assertion matches only when it has the same `Format`, as
Core §3.3.4 strong matching requires. Before, a value match was enough. An
`unspecified` `Format` on the logout still compares values only, because an
omitted `Format` means `unspecified` (Core §2.2.2).

## Add the status to a hand-built `FlowResult`

`LogoutResponse::try_from(FlowResult)` now reads the top-level status code
from the extract. It returns `SamlError::ProtocolProfile` when `statusCode` is
missing, or when it is not `Success`, `Requester`, `Responder`, or
`VersionMismatch`.

A `FlowResult` returned by the raw logout parsers already carries these
fields. If you build the extract yourself, add the top-level code, and the
subordinate code when the response has one:

```rust
use saml_rs::constants::status_code;
use saml_rs::util::Value;

let status_fields = [
	("statusCode".to_string(), Value::Str(status_code::SUCCESS.to_string())),
	(
		"subordinateStatusCode".to_string(),
		Value::Str(status_code::PARTIAL_LOGOUT.to_string()),
	),
];
```

## Order the children of a `ManageNameIDRequest`

This section applies to identity providers that call
`receive_name_id_management`, and to either role calling
`receive_name_id_management_redirect`.

A received `ManageNameIDRequest` must now follow the protocol schema sequence:
at most one `Issuer`, one `ds:Signature`, and one `Extensions`, in that order,
then the identifier and the change. Another order, such as `Extensions` after
`Terminate` or before `Issuer`, or a second `Issuer`, `Signature`, or
`Extensions`, now returns `SamlError::ProtocolProfile`. Before, those elements
were skipped wherever they appeared. If a peer sends such a request, ask it to
send the schema order.

## Expect padded persistent and transient formats to be checked

This section applies if a `NameId` you send, or the NameID format you
configure, is a `NameIdFormat::Custom` URI that names the persistent or
transient format with surrounding whitespace. Other formats are not affected.

The format is now compared after the `xs:anyURI` whitespace collapse, as it
already was for the absolute URI check. A padded transient format now makes
`start_name_id_management` and `start_name_id_management_redirect` return
`SamlError::ProtocolProfile`. A padded persistent or transient format with a
value longer than 256 characters now makes those methods and every login
response (`respond_sso`, `initiate_sso`, `respond_sso_artifact`,
`initiate_sso_artifact`, `respond_paos_sso`, and the raw login response) return
`SamlError::Invalid`. A
`ManageNameIDRequest` for a padded persistent identifier without qualifiers
now carries the default `NameQualifier` and `SPNameQualifier`. Use
`NameIdFormat::Persistent` or `NameIdFormat::Transient` to write the format
without the padding.

## Expect a future bearer `NotBefore` to be rejected

Bearer `SubjectConfirmationData@NotBefore` is now checked when present. A
bearer confirmation whose `NotBefore` is later than now plus the
`NotBefore` clock skew, or whose `NotBefore` cannot be read as a timestamp
(as for bearer `NotOnOrAfter`), no longer confirms the assertion. When no other bearer confirmation is
satisfied, the response fails with `SamlError::SubjectConfirmationInvalid`
and `SubjectConfirmationReason::TimeWindowInvalid`. Before, the attribute was
ignored. A namespace-qualified `NotBefore` attribute on
`SubjectConfirmationData` now returns `SamlError::ProtocolProfile`, as other
qualified copies of the attributes the library reads already do.

This affects service providers that accept responses through the typed
`finish_sso` and `accept_unsolicited_sso` flows, `finish_paos_sso`, or the raw
`parse_login_response` family. If an identity provider sends a bearer
`NotBefore` ahead of your clock, synchronize the clocks or widen
`ClockSkew::with_not_before_millis`. A `NotBefore` that has been reached is
still accepted.

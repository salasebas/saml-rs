# How to upgrade from 0.7 to 0.8

Use this guide to upgrade `saml-rs`, `opensaml`, `samlify`, or `samlet` from
the latest `0.7.x` release to `0.8.x`. Apply only the sections that affect
your integration. The [changelog](../../CHANGELOG.md) lists compatible
additions.

## Give each ACS its own index

This and the next two sections apply if you generate service provider or
identity provider metadata through `Saml::sp`, `ServiceProvider::from_config`,
`IdentityProvider::from_config`, `generate_sp_metadata`, `generate_idp_metadata`,
or `try_generate_idp_metadata`. Metadata you import is not affected. See
[metadata rules](../conformance/metadata-and-replay.md).

Two `AssertionConsumerService` endpoints with the same explicit index now
return `SamlError::Invalid`. Before, the metadata published both, and looking
up that index failed. Set a different index with `AcsEndpoint::with_index`,
or `Endpoint::index` on raw configuration, or leave one unset.
More than 65,536 `AssertionConsumerService` endpoints now return
`SamlError::Invalid` too, because no `unsignedShort` index is left.

## Check the index of an ACS without one

An ACS without an explicit index is still written with its position in the
list. When an explicit index on another ACS already uses that position, the
ACS now gets the smallest index no other ACS uses. Before, both endpoints
were written with the same index.

Metadata that already had unique indexes is written unchanged. If you
published metadata with a duplicate index, check which index each ACS has
now. Update peers or stored `AssertionConsumerServiceIndex` values that
expected the old one. To keep an index stable, set it explicitly.

## Stop relying on `isDefault` outside ACS

`Endpoint::is_default` now writes `isDefault` on `AssertionConsumerService`
only. `SingleSignOnService`, `SingleLogoutService`, and `ManageNameIDService`
no longer carry it, because the metadata schema does not define it on them.
If a peer read the flag on one of them, tell it which endpoint to use.

## Remove Unicode whitespace before `base64_decode`

`base64_decode` now ignores the same whitespace as `base64_decode_with_limit`:
space, tab, line feed, form feed, and carriage return. Vertical tab, no-break
space, line separator, ideographic space, and every other Unicode whitespace
character now return `SamlError::Base64`. Line-wrapped base64 still decodes.

This affects callers that pass base64 containing those characters to
`saml_rs::binding::base64_decode` or `saml_rs::crypto::verify_message_signature`.
HTTP-Redirect and HTTP-POST-SimpleSign reception now reject a `Signature`
value that contains them.

If an integration must accept that input, remove the characters before
decoding:

```rust
let cleaned: String = input.split_whitespace().collect();
let bytes = saml_rs::binding::base64_decode(&cleaned)?;
```

## Pass `RespondPaosSso` to `respond_paos_sso`

This section applies when an identity provider answers Enhanced Client/Proxy
login with `Saml<Idp>::respond_paos_sso`. Service providers and `reject_paos_sso`
callers need no change.

`respond_paos_sso` takes a fourth argument, `RespondPaosSso`. Pass
`RespondPaosSso::default()` to keep the previous response, which has no
`AttributeStatement`:

```rust
let answered = idp.respond_paos_sso(&sp, &received, subject, RespondPaosSso::default())?;
```

To send attributes, set them on the options. They are written the same way as
`RespondSso::attributes`:

```rust
let answered = idp.respond_paos_sso(
	&sp,
	&received,
	subject,
	RespondPaosSso::default().attributes(attributes),
)?;
```

`respond_paos_sso` now returns `SamlError::Invalid` when these attributes are
combined with a login response template, or when a basic attribute name is not
an XML name.

## Compare the received NameID with its attributes

This and the next section apply if your integration reads a typed
`LogoutRequest` NameID, or builds a typed `LogoutResponse` from a `FlowResult`
you assembled yourself. `LogoutResponse::status` is a compatible addition.

`LogoutRequest::name_id` now returns the `Format`, `NameQualifier`,
`SPNameQualifier`, and `SPProvidedID` of the received `<NameID>`. Before, it
returned the value with no attributes.

Check code that compares the received `NameId` with a stored one using `==`.
The comparison now includes every attribute, so a stored `NameId` without the
attributes the peer sends no longer compares equal. Store the `NameId` from the
accepted assertion, which carries the same attributes, or compare
`NameId::value` when your session lookup is by value only.

An `OutstandingLogout` built from the received `NameId` now carries its
`Format`. A later assertion matches only when it has the same `Format`, as
Core §3.3.4 strong matching requires. Before, a value match was enough. An
`unspecified` `Format` on the logout still compares values only, because an
omitted `Format` means `unspecified` (Core §2.2.2).

## Add the status to a hand-built `FlowResult`

`LogoutResponse::try_from(FlowResult)` now reads the top-level status code
from the extract. It returns `SamlError::ProtocolProfile` when `statusCode` is
missing, or when it is not `Success`, `Requester`, `Responder`, or
`VersionMismatch`.

A `FlowResult` returned by the raw logout parsers already carries these
fields. If you build the extract yourself, add the top-level code, and the
subordinate code when the response has one:

```rust
use saml_rs::constants::status_code;
use saml_rs::util::Value;

let status_fields = [
	("statusCode".to_string(), Value::Str(status_code::SUCCESS.to_string())),
	(
		"subordinateStatusCode".to_string(),
		Value::Str(status_code::PARTIAL_LOGOUT.to_string()),
	),
];
```

## Order the children of a `ManageNameIDRequest`

This section applies to identity providers that call
`receive_name_id_management`, and to either role calling
`receive_name_id_management_redirect`.

A received `ManageNameIDRequest` must now follow the protocol schema sequence:
at most one `Issuer`, one `ds:Signature`, and one `Extensions`, in that order,
then the identifier and the change. Another order, such as `Extensions` after
`Terminate` or before `Issuer`, or a second `Issuer`, `Signature`, or
`Extensions`, now returns `SamlError::ProtocolProfile`. Before, those elements
were skipped wherever they appeared. If a peer sends such a request, ask it to
send the schema order.

## Expect padded persistent and transient formats to be checked

This section applies if a `NameId` you send, or the NameID format you
configure, is a `NameIdFormat::Custom` URI that names the persistent or
transient format with surrounding whitespace. Other formats are not affected.

The format is now compared after the `xs:anyURI` whitespace collapse, as it
already was for the absolute URI check. A padded transient format now makes
`start_name_id_management` and `start_name_id_management_redirect` return
`SamlError::ProtocolProfile`. A padded persistent or transient format with a
value longer than 256 characters now makes those methods and every login
response (`respond_sso`, `initiate_sso`, `respond_sso_artifact`,
`initiate_sso_artifact`, `respond_paos_sso`, and the raw login response) return
`SamlError::Invalid`. A
`ManageNameIDRequest` for a padded persistent identifier without qualifiers
now carries the default `NameQualifier` and `SPNameQualifier`. Use
`NameIdFormat::Persistent` or `NameIdFormat::Transient` to write the format
without the padding.

## Expect a future bearer `NotBefore` to be rejected

Bearer `SubjectConfirmationData@NotBefore` is now checked when present. A
bearer confirmation whose `NotBefore` is later than now plus the
`NotBefore` clock skew, or whose `NotBefore` cannot be read as a timestamp
(as for bearer `NotOnOrAfter`), no longer confirms the assertion. When no other bearer confirmation is
satisfied, the response fails with `SamlError::SubjectConfirmationInvalid`
and `SubjectConfirmationReason::TimeWindowInvalid`. Before, the attribute was
ignored. A namespace-qualified `NotBefore` attribute on
`SubjectConfirmationData` now returns `SamlError::ProtocolProfile`, as other
qualified copies of the attributes the library reads already do.

This affects service providers that accept responses through the typed
`finish_sso` and `accept_unsolicited_sso` flows, `finish_paos_sso`, or the raw
`parse_login_response` family. If an identity provider sends a bearer
`NotBefore` ahead of your clock, synchronize the clocks or widen
`ClockSkew::with_not_before_millis`. A `NotBefore` that has been reached is
still accepted.

## Choose valid, distinct tag prefixes

This section applies if you set `tag_prefix_protocol` or
`tag_prefix_assertion` on `EntitySetting` or `TemplatePolicy`.

Each prefix must now be an XML NCName other than `xml` and `xmlns`, and the
two prefixes must differ. Otherwise generating a login response, a logout
request or response, or a NameID management message returns
`SamlError::Invalid`. Before, a prefix such as `1a`, `a,b`, `-x`, `xml`, or
`xmlns` was accepted and produced XML that does not parse, or failed later
with a different error. Pick a prefix that starts with a letter or `_` and
contains only letters, digits, `_`, `-`, or `.`.

A custom login response, logout request, or logout response template is now
rewritten in one pass. With `tag_prefix_protocol = "saml"`, the template's
`samlp:` elements now take `saml:`. Before, they were rewritten again to
`tag_prefix_assertion`, and the root declared that prefix twice.

## Issue a subject without confirmations

This applies if your identity provider passes a `Subject` with
`SubjectConfirmation` values to `respond_sso`, `initiate_sso`,
`respond_sso_artifact`, `initiate_sso_artifact`, or `respond_paos_sso`.

These methods now return `SamlError::Unsupported` for such a subject. Before,
they dropped the confirmations and wrote only their own bearer confirmation,
so a holder-of-key confirmation you supplied never reached the service
provider.

Build the subject with no confirmations. The response is the same one the
earlier version sent:

```rust
use saml_rs::{NameId, Subject};

let subject = Subject::new(NameId::new("alice@example.com", None), Vec::new());
```

A proxy that re-issues the subject of an accepted login is affected too: that
subject carries the upstream bearer confirmation. Keep its `NameId` and drop
the confirmations:

```rust
let subject = Subject::new(session.subject().name_id().clone(), Vec::new());
```

## Drop `RespondSlo::relay_state`

This and the next section apply if you answer or finish typed Single Logout
with `respond_slo` or `finish_slo`. See
[Single Logout rules](../conformance/single-logout.md).

`RespondSlo::relay_state` is removed. `respond_slo` now always writes the
exact RelayState that arrived with the `LogoutRequest`, as Bindings §3.1.1
requires of a responder. Before, the setter could replace or drop it.

Remove the call. If you passed the received or stored RelayState back, the
response is unchanged:

```rust
let response = idp.respond_slo(&sp, &received, RespondSlo::post())?;
```

If you replaced or suppressed the RelayState, keep that state on your side,
for example in a session keyed by the RelayState you sent. Adding a
RelayState to a response whose request had none is no longer possible either.
`RespondSlo::soap` still returns `SamlError::ProtocolProfile` for a request
that carried RelayState, because SOAP cannot return it, and suppressing the
RelayState no longer avoids that error. Answer that request over a
front-channel binding.

## Accept a logout response over another front-channel binding

`finish_slo` now accepts a response to an HTTP-Redirect, HTTP-POST, or
HTTP-POST-SimpleSign request over any of those three bindings, as Profiles
§4.4.3.4 and §4.4.3.5 allow. Before, a response over a different binding
returned `SamlError::UnsupportedBinding`. The `Destination` is now checked
against your `SingleLogoutService` for the binding the response arrived on.
A response over a front-channel binding your metadata does not publish
returns `SamlError::MissingMetadata`.

A SOAP response to a front-channel request, or a front-channel response to a
SOAP request, still returns `SamlError::UnsupportedBinding`. If your
deployment relied on that error to refuse a binding, stop publishing a
`SingleLogoutService` for it.

## Size `XmlPolicy::limits` for SOAP envelopes

This and the next section apply if you receive SOAP through
`answer_artifact_resolve`, `ArtifactResolution::finish`, `receive_slo` or
`finish_slo` with `BrowserInput::soap`, `receive_name_id_management`, or
`StartedNameIdManagement::finish`.

These calls now read the whole SOAP envelope, header included, under the
`XmlPolicy::limits` configured on the `Saml` instance. Before, they used
`XmlLimits::default()`. An envelope over a configured limit now returns
`SamlError::Invalid` with `ERR_XML_LIMIT_EXCEEDED`. A limit above the default
now admits a larger envelope.

If you set limits below the defaults, check that they still fit the largest
envelope your peers send. `SoapProtocolMessage::from_envelope` and the
`HttpRequest` conversions from `BrowserInput` have no configuration and keep
the defaults.

## Send one SOAP `Header` before the `Body`

The SOAP envelope reader now returns `SamlError::ProtocolProfile` when a
`Header` follows the `Body` or the envelope has more than one `Header`. This
applies to the calls in the previous section and to
`SoapProtocolMessage::from_envelope`. An envelope with two `Body` elements,
one of them empty, now returns `SamlError::ProtocolProfile` instead of
`SamlError::Xml`. The ECP reader already refused these envelopes.

SOAP 1.1 §4 requires a `Header` to be the first child of `Envelope` and the
`Body` to follow it. If a peer sends another order, ask it to send a SOAP 1.1
envelope. See [SOAP envelope rules](../conformance/artifact-resolution.md).

## Expect signatures in SOAP messages to be verified where they sit

This section applies if you receive SAML messages over SOAP: logout requests
and responses through `receive_slo` and `finish_slo`, NameID management
through `receive_name_id_management` and `StartedNameIdManagement::finish`,
and artifact resolution through `answer_artifact_resolve` and
`ArtifactResolution::finish`. PAOS is not affected.

The message read from a SOAP body now declares every namespace in scope from
its ancestors, including the envelope's, and its signature is verified against
that element. Inclusive Canonical XML (`REC-xml-c14n-20010315`) takes those
declarations into the digest, so a verifier now computes it as it would on the
message in place in the envelope. A message the peer signed alone with
Canonical XML, or with exclusive canonicalization and an `InclusiveNamespaces`
`PrefixList` naming a prefix the envelope declares, and then wrapped in SOAP,
now fails with `SamlError::SignatureVerification` and
`SignatureVerificationReason::XmlSignature`. Before, it was accepted. A message
signed with Canonical XML as it sits in the envelope is now accepted. Before,
it was rejected.

Messages signed with exclusive canonicalization and no such `PrefixList`,
which saml-rs and most peers use, are not affected. If a peer signs a
standalone message with Canonical XML, ask it to sign with exclusive
canonicalization, as SAML Core §5.4.3 and §5.4.4 recommend, or to sign the
message in place in the envelope.

The strings returned by `SoapProtocolMessage::xml()` and
`ResolvedProtocolMessage::xml()`, and a decrypted assertion, now carry these
inherited `xmlns` declarations, such as `xmlns:soap` from the envelope or the
`Response` namespaces on an assertion. Parse them as XML rather than comparing
them as text.

## Send well-formed, namespace-well-formed XML

This section applies to every input `saml-rs` parses: received messages,
metadata, SOAP and PAOS envelopes, `saml_rs::context::is_valid_xml`, and
`saml_rs::xml::dom::parse`, `parse_with_limits`, `parse_roots`, and
`parse_roots_with_limits`. Well-formed input is not affected.

These inputs now return `SamlError::Xml`, as XML 1.0 and Namespaces in XML
require of a parser. Before, the DOM accepted them, and only the parser behind
signature verification and decryption rejected them:

- an element that is still open at the end of the input, such as
  `<Root/><Second>`, including in `parse_roots`;
- `<` in an attribute value;
- a character outside the XML character range, written directly or as a
  character reference: a control character other than tab, line feed, and
  carriage return, U+FFFE, or U+FFFF;
- `--` inside a comment;
- a namespace prefix that the document does not declare;
- a binding of the `xmlns` prefix, a binding of `xml` to another namespace, or
  another prefix or the default namespace bound to the `xml` or `xmlns`
  namespace;
- two attributes on one element with the same namespace and local name.

A namespace name is compared after its character and entity references are
resolved, so `xmlns:b="&#x75;rn:a"` binds `urn:a`.

A received message whose root, or a SAML element such as `<Assertion>`, uses
an undeclared prefix now returns
`SamlError::Xml` before protocol-profile validation. Before, it returned
`SamlError::ProtocolProfile`. Update a `match` that expected that variant.

The DOM now limits the namespace bindings in scope at once to
`XmlLimits::max_attributes_per_element`, 64 by default, as protocol-profile
validation already did for messages. More return `SamlError::Invalid` with
`ERR_XML_LIMIT_EXCEEDED`. Before, a received message over that limit returned
`SamlError::Xml` from protocol-profile validation, and metadata had no limit.
Update a `match` that expected `SamlError::Xml`. Raise
`max_attributes_per_element` if a metadata document you trust declares more.

`saml_rs::xml::extract` and `extract_with_limits` still accept one element cut
out of a larger document, such as an extracted `context` value, whose prefixes
are declared on an ancestor outside it. The other checks above apply to it.

No option accepts the rejected input. Ask the peer to fix the XML it sends.

The DOM still accepts some input that the parser behind signature verification
and decryption rejects: `]]>` in text, attributes with no whitespace between
them, a name that starts with a digit, and an XML declaration that is not at
the very start of the input.

## State the authentication context an exact request asks for

This section applies if your identity provider answers with
`respond_sso` and `apply_web_browser_sso_generation_rules`, with
`respond_sso_artifact` under those rules, or with `respond_paos_sso`. See
[generation rules](../conformance/web-browser-sso-generation.md#identity-provider-response).

The typed `AuthnRequest` now reads `RequestedAuthnContext`. When its
`Comparison` is `exact` or omitted, a success response now returns
`SamlError::Invalid` unless the authentication context it writes is one of
the requested references. Before, the request was ignored and the response
claimed the unspecified class. Read `AuthnRequest::requested_authn_context`,
then either pass the context the subject was authenticated with:

```rust
let options = RespondSso::post()
    .apply_web_browser_sso_generation_rules()
    .authn_context(AuthnContextReference::class(
        "urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport",
    )?);
```

or, when no requested context can be met, answer with an error status:

```rust
let options = RespondSso::post()
    .status(Status::responder().with_subordinate(SubordinateStatusCode::no_authn_context()));
```

For PAOS, use `RespondPaosSso::authn_context`, or `reject_paos_sso` with the
same status. Requests with another comparison, or without
`RequestedAuthnContext`, are answered as before.

`RespondSso::authn_context` without `apply_web_browser_sso_generation_rules`
returns `SamlError::Invalid`, because that response has no `AuthnStatement`.

`receive_sso` and `receive_paos_sso` now return `SamlError::Invalid` for a
`RequestedAuthnContext` outside its schema: a `Comparison` other than
`exact`, `minimum`, `maximum`, or `better`, no references, both class and
declaration references, or a second `RequestedAuthnContext`. A
namespace-qualified `Comparison` or a reference in another namespace returns
`SamlError::ProtocolProfile`; those two rejections also apply to raw request
parsing (`flow`, `parse_login_request`) and the compatibility crates. Before,
the element was not read.

The raw `authnContextClassRef` extract key now holds the class references
inside `RequestedAuthnContext`. Before, it read a path that a valid request
never has, and was empty. `requestedAuthnContext`,
`requestedAuthnContextComparison`, and `authnContextDeclRef` are new keys.

## Expect unsolicited responses without `InResponseTo`

This section applies if your identity provider sends unsolicited login
responses through `initiate_sso`, `initiate_sso_artifact`, or the raw
`create_login_response` without `in_response_to`, or if a login response
template contains `InResponseTo="{InResponseTo}"`.

An unsolicited response now omits `InResponseTo` on the `Response` and on the
bearer `SubjectConfirmationData`. Before, samlify-port generation and
templates wrote `InResponseTo=""`, which the schema does not allow. An
`in_response_to` of `Some("")` is treated as no request. A template element
whose text is only `{InResponseTo}` is removed when there is no request, as
`{NameIDFormat}` already is. Solicited responses are unchanged.

If a peer service provider or a test matched the empty attribute, update it
to expect no `InResponseTo`.

## Reject an empty `InResponseTo` on typed unsolicited SSO

This section applies if a service provider accepts IdP-initiated responses
with `accept_unsolicited_sso` or
`accept_unsolicited_sso_with_outstanding_logout`.

A `Response` or bearer `SubjectConfirmationData` with `InResponseTo=""` now
returns `SamlError::InResponseToMismatch` with `expected: None` and
`actual: Some("")`. Before, an empty attribute was read as absent and the
response was accepted.

If a third-party identity provider sends `InResponseTo=""` on unsolicited
responses, ask it to omit the attribute. Until it does, the raw
`parse_unsolicited_login_response` still reads an empty value as absent.

## Add `lifetime` to metadata configuration literals

This section applies if you build the typed `SpMetadataConfig` or
`IdpMetadataConfig` as a struct literal, or the raw ones as a struct literal
without `..Default::default()`.

Both configurations have a new `lifetime: Option<MetadataLifetime>` field. Set
it to `None` to keep the previous metadata, which has neither `validUntil` nor
`cacheDuration`. Metadata §2.3.1 and §2.3.2 require one of them on the root
element, so prefer setting it:

```rust
use std::time::Duration;
use saml_rs::MetadataLifetime;

let lifetime = Some(MetadataLifetime::CacheDuration(Duration::from_secs(86_400)));
```

The config builders take the same value through `metadata_lifetime`.

A `MetadataLifetime::ValidUntil` instant is fixed when `Saml` is built, so
build a new `Saml` before it passes, or use `MetadataLifetime::CacheDuration`.

## Refresh peer metadata before its `validUntil`

This section applies if you import peer metadata into `IdpDescriptor` or
`SpDescriptor` and that metadata carries `validUntil`. Metadata without
`validUntil` is not affected, and an elapsed `cacheDuration` does not make
metadata unusable. See [metadata rules](../conformance/metadata-and-replay.md).

Every typed flow now refuses a descriptor once the earliest `validUntil` of
the peer's role descriptor, its `EntityDescriptor`, and any enclosing
`EntitiesDescriptor` has been reached. It returns `SamlError::TimeWindowInvalid`
with `TimeWindowField::MetadataValidUntil`. Flows that take a
`SamlValidationContext` compare with its clock. The others, such as
`start_sso`, `respond_sso`, and `start_slo`, compare with the system clock.
Before, the attribute was ignored and expired metadata stayed in use.

Import now returns the same error when a `validUntil` it reads is not an
`xs:dateTime` with a timezone, such as `2030-01-01T00:00:00` without `Z`. As
library policy, it also rejects hour 24 (`2030-01-01T24:00:00Z`), a leap
second other than 23:59:60 UTC on the last day of a month, and a year outside
0001 through 9999, although XML Schema allows them.

Fetch fresh metadata from the publisher and import it again. If a peer
publishes a value without a timezone or one of these values, ask it to
publish a UTC instant such as `2030-01-01T00:00:00Z`.

## Handle correlation errors on an SSO error response

This applies to `finish_sso`, `finish_sso_with_outstanding_logout`,
`accept_unsolicited_sso`, `accept_unsolicited_sso_with_outstanding_logout`,
`finish_paos_sso`, and the raw `parse_login_response`,
`parse_login_response_with_request_id`, `parse_unsolicited_login_response`,
and `flow` with `ParserType::SamlResponse`.

A `Response` with a status other than `Success` now returns
`SamlError::StatusNotSuccess` only after a present signature verifies and its
`Issuer`, `InResponseTo`, and `Destination` checks pass. Before, the status
came first. The response still does not need a signature, and a missing
`Issuer` is accepted. A response that fails one of those checks now returns
that check's error:

| Error response | Before | Now |
| --- | --- | --- |
| Present signature does not verify | `StatusNotSuccess` | `SignatureVerification` |
| Wrong `Issuer` | `StatusNotSuccess` | `IssuerMismatch` |
| Wrong or missing `InResponseTo` | `StatusNotSuccess` | `InResponseToMismatch` |
| Wrong `Destination`, or signed without one | `StatusNotSuccess` | `DestinationMismatch` |

Who must change: callers that match `StatusNotSuccess` to show a login
failure from the identity provider. Treat these errors as a failed login too.
`StatusNotSuccess` now means the response came for this login and this
service provider. Without a signature it is still not proof of who sent it.

## Use a URI of at most 1024 characters as your entity ID

This section applies if you build `SpConfig` or `IdpConfig`, call
`Saml::sp`, `Saml::idp`, `EntityId::try_new`, `EntityId::from_str`, or
`EntityId::try_from`, generate metadata with `generate_sp_metadata`,
`generate_idp_metadata`, or `try_generate_idp_metadata`, or build a raw
provider with `ServiceProvider::from_config` or
`IdentityProvider::from_config`. See
[entity identifiers](../conformance/identifiers.md#entity-identifiers).

These now return `SamlError::Invalid` when the entity ID is not an absolute
URI reference, is longer than 1024 characters, or has leading or trailing
whitespace, a tab, a line break, or consecutive spaces. Before, they accepted any
value with a non-whitespace character, and raw metadata generation also
accepted an empty `entity_id`, which is what `SpMetadataConfig::default()`
and `IdpMetadataConfig::default()` hold. Building the config, or generating
the metadata, now fails for such a value.

Give your own service provider or identity provider an absolute URI, such as
`https://sp.example.com/metadata` or `urn:example:sp`, and trim surrounding
whitespace from a value you read from configuration. Changing it changes the
`entityID` and `Issuer` your peers see, so register the new value with them.
In raw `SpMetadataConfig` and `IdpMetadataConfig`, set `entity_id`
explicitly.

A peer's entity ID is not affected. Imported metadata and received `Issuer`
values are read as before. To name a peer whose entity ID is not a URI, such
as the expected entity ID passed to `IdpDescriptor::from_metadata_xml_for`,
use `EntityId::new`.

## Read each attribute by `Name` and `NameFormat`

This section applies to service providers that read `SsoSession::attributes`.

`<Attribute>` elements with the same `Name` and a different `NameFormat` are
now separate `Attribute` entries, as Errata 05 E49 identifies an attribute by
both. Before, they were one entry with the `NameFormat` of the first element
and the values of all of them. `Attributes::get` returns the first entry with
a name. If an identity provider sends one name in more than one format, look
the attribute up by both:

```rust
let role = session.attributes().as_slice().iter().find(|attribute| {
	attribute.name() == "role" && attribute.format() == Some(&AttributeNameFormat::Uri)
});
```

An omitted `NameFormat` and `unspecified` are still one attribute. Every value
of repeated elements with the same `Name` and `NameFormat` is now kept. Before,
the values of a repeated element after the first were dropped when that
element had more than one value.

Each `attributeNameFormats` entry of raw `FlowResult::extract` now has an
`attributeValue` array with the element's values. Allow the new key when you
compare or iterate over those entries.

If you build a `FlowResult` yourself and convert it to `SsoSession`, give each
`<Attribute>` an `attributeNameFormats` entry with `name`, `nameFormat` when it
has one, and `attributeValue`. The typed attributes come from those entries.
An extract with `attributes` and no `attributeNameFormats`, or an entry without
`attributeValue`, now returns `SamlError::Invalid`.

## Give each attribute an absolute `NameFormat`

This section applies to identity providers that send attributes through
`RespondSso::attributes` or `RespondPaosSso::attributes`.

A `NameFormat` that is blank or not an absolute URI reference, such as
`not a uri` or `/relative/path`, now returns `SamlError::Invalid` instead of
being written. Core §1.3.2 requires an absolute URI. Use one of the
`AttributeNameFormat` variants, a deployment URI such as
`https://example.com/attribute-name-format`, or `None` to omit `NameFormat`.

## Expect `SPNameQualifier` in a received `NameIDPolicy`

This section applies if your identity provider receives an `AuthnRequest`.

`AuthnRequest::name_id_policy` after `receive_sso` or `receive_paos_sso` now
keeps `SPNameQualifier`, returned by `NameIdPolicy::sp_name_qualifier`. A `NameIDPolicy` with only
`SPNameQualifier` is now `Some`. Before, it was `None`, as if the request had
no policy. How to answer such a request is in
[Issue the requested `SPNameQualifier`](#issue-the-requested-spnamequalifier).

A namespace-qualified `SPNameQualifier` on `NameIDPolicy` now returns
`SamlError::ProtocolProfile` from `receive_sso`, `receive_paos_sso`, and raw
request parsing (`flow`, `parse_login_request`), as qualified copies of the
other attributes the library reads already do. Before, it was ignored. The raw
`nameIDPolicy` extract object now carries a `spNameQualifier` key when the
attribute is present.

## Issue the requested `SPNameQualifier`

This section applies if your identity provider issues a `NameId` through
`respond_sso`, `initiate_sso`, `respond_sso_artifact`, `initiate_sso_artifact`,
or `respond_paos_sso`.

The issued `<NameID>` now carries the `NameQualifier` and `SPNameQualifier` of
the `NameId`. Before, both were dropped. The service provider reads them back
from `SsoSession::name_id`. If you set them only for your own records, build
the `NameId` with `NameId::new` or pass `None` for them.

A success response to an `AuthnRequest` whose `NameIDPolicy` has an
`SPNameQualifier` and a SAML-defined `Format` other than `unspecified` now
returns `SamlError::Invalid` unless the `NameId` has that same
`SPNameQualifier`. This applies under
`RespondSso::apply_web_browser_sso_generation_rules` and always in
`respond_paos_sso`. Errata 05 E15 requires the two values to be identical.
When you can return an identifier in the requested namespace, issue it with that
qualifier. Otherwise, answer with an error status:

```rust
use saml_rs::constants::status_code;

let requested = received
    .message()
    .name_id_policy()
    .and_then(NameIdPolicy::sp_name_qualifier);
let options = match requested {
    Some(namespace) if !serves_namespace(namespace) => RespondSso::post()
        .apply_web_browser_sso_generation_rules()
        .status(Status::responder().with_subordinate(
            SubordinateStatusCode::try_new(status_code::INVALID_NAME_ID_POLICY)?,
        )),
    Some(_) | None => RespondSso::post().apply_web_browser_sso_generation_rules(),
};
let name_id = NameId::with_qualifiers(
    stored_persistent_value,
    Some(NameIdFormat::Persistent),
    None,
    requested.map(str::to_string),
    None,
);
```

A `NameId` with `NameQualifier` or `SPNameQualifier` and a login response
template now returns `SamlError::Invalid`, as `SPProvidedID` already did.
Before, the template dropped them.

## Check custom subordinate status codes against the URI rule

This section applies if you pass your own URI to
`SubordinateStatusCode::try_new`, or if a custom `LogoutResponse` template
writes `Consent`, a `StatusCode` `Value`, or the `Issuer`.

These values are now read as an absolute URI reference by the rule a NameID
`Format` already follows: RFC 2396 with RFC 2732 IPv6 hosts, after the
`xs:anyURI` escaping of XML Schema 1.0. Before, they were parsed as WHATWG
URLs. `try_new` still rejects whitespace and the characters `&`, `"`, `'`,
`<`, and `>`, and the outbound check still rejects whitespace. `Destination`
is still parsed as a URL.

`try_new` now returns `SamlError::Invalid`, and `respond_slo` returns
`SamlError::ProtocolProfile` from its outbound check, for a value that:

- has nothing after the scheme, such as `urn:` or `mailto:`;
- has a `%` that is not followed by two hexadecimal digits, such as
  `urn:example:%zz`;
- has a second `#`, such as `urn:example:a#b#c`;
- has `[` or `]` in a path or at the start of an opaque part, such as
  `https://idp.example/a[b]` or `urn:[a]`;
- has a character XML 1.0 cannot carry, such as U+0001.

Before, these were accepted, and a non-XML character produced a message the
peer could not parse. A value with a host or port the URL parser refused,
such as an empty host, a non-numeric port, or a port above 65535, as in
`https://idp.example:70000/status`, is now accepted. Before, it was rejected.

If a value of yours is now rejected, percent-encode the character as `%HH` or
use a URI such as `urn:example:status:local-failure`.

## Give `IssuedArtifacts` a lifetime

This section applies if you issue artifacts with `issue_artifact`,
`respond_sso_artifact`, or `initiate_sso_artifact`.

`IssuedArtifacts::new()` and its `Default` implementation are removed.
Construct the store with `IssuedArtifacts::expire_after(lifetime)`. An
`ArtifactResolve` that arrives after the lifetime now gets Success without the
message, and `AnsweredArtifact::release` reports
`ArtifactWithheld::NotOutstanding`. Before, an unresolved artifact resolved
until you called `IssuedArtifacts::remove`. Each issue now drops the artifacts
issued more than one lifetime ago, so you no longer need to remove them to
bound memory.

```rust
use std::time::Duration;

use saml_rs::IssuedArtifacts;

let mut issued = IssuedArtifacts::expire_after(Duration::from_secs(60));
```

SAML Core §3.5.3 asks the artifact issuer for the shortest practical time
limit. Choose the time a service provider needs to receive the artifact and
send `ArtifactResolve`. Keep the `ArtifactUses::enforce_single_use` period on
the service provider longer than that lifetime.

## Add `additional_decryption_keys` to a `Credentials` literal

This section applies if you build `Credentials` with a struct literal that
names every field and has no `..Credentials::default()`.

`Credentials` has a new field, `additional_decryption_keys`, so such a literal
no longer compiles. Add `additional_decryption_keys: Vec::new()` to keep
today's behaviour, or end the literal with `..Credentials::default()`. A
literal that already ends with `..Credentials::default()` is not affected.

To roll over an encryption key:

1. Put the next key and its certificate in a `DecryptionCredential` in that
   list. Metadata publishes both certificates, and decryption tries
   `decryption_key` first, then each additional key.
2. Make the next key the `decryption_key` and `encryption_certificate`, and
   move the old key and certificate into the list. A peer that encrypts for
   the first published certificate, as saml-rs does, now uses the new one.
3. Once every peer has refreshed your metadata, remove the old key. A
non-empty list without a `decryption_key` returns
`SamlError::MissingKey("decryption_key")` from the config builders.

## Update `bergshamra` to 0.12 if you depend on it directly

This section applies if your crate also depends on `bergshamra`, for example to
name the `bergshamra::keys::Key` that `saml_rs::crypto::keys::load_private_key`
returns and that `construct_saml_signature`, `construct_message_signature`, and
`decrypt_assertion` take. Integrations that only call `saml-rs` are not
affected.

The `crypto-rustcrypto`, `crypto-aws-lc`, and `crypto-fips` features now use
Bergshamra 0.12.0. A `Key` from a `bergshamra` 0.11 dependency is a different
type from the one `saml-rs` takes, so that code no longer compiles. Set
`bergshamra = "0.12"` in your manifest and apply the
[Bergshamra 0.12.0 changelog](https://github.com/kushaldas/bergshamra/blob/v0.12.0/CHANGELOG.md)
to your direct calls.

Through `saml-rs`, RSA keys shorter than 1024 bits give the same results as in
0.7:

- A peer certificate with such a key verifies no signature on any provider and
  returns `SamlError::Crypto`. Only the error message changes.
- A local private key with such a key still loads, signs, and decrypts on the
  default `crypto-bergshamra` feature. AWS-LC and FIPS still reject it.

## Expect `StrictRsaSha2` on detached and identity provider signatures

This section applies if you select `XmlSignatureProfile::StrictRsaSha2`,
write an `IdpValidationPolicy` struct literal, or set
`FlowOptions::strict_xml_signature_profile`. See
[inbound XML signature verification](../conformance/xml-security-algorithms.md#inbound-xml-signature-verification).

`StrictRsaSha2` now also applies to the detached `SigAlg` of an HTTP-Redirect
or HTTP-POST-SimpleSign message. A `SigAlg` other than RSA-SHA256, RSA-SHA384,
or RSA-SHA512 returns `SamlError::AlgorithmUnsupported`. Before, any `SigAlg`
the crypto provider supported verified. If a peer signs its Redirect or
SimpleSign messages with RSA-SHA1, ask it to move to RSA-SHA256, or select
`AllowProviderSupportedForCompatibility`.

`IdpValidationPolicy` has a new `xml_signatures` field. Compatibility sets it
to `AllowProviderSupportedForCompatibility`, so an identity provider on that
preset verifies what it verified before. Recommended sets it to
`ExcludeWeakAlgorithms`; the next section says what that rejects. A struct literal must set
the field or end with `..IdpValidationPolicy::recommended()`. With
`StrictRsaSha2`, the identity provider applies the profile to the
`AuthnRequest` and logout messages it receives.

```rust
use saml_rs::{IdpValidationPolicy, XmlSignatureProfile};

let validation = IdpValidationPolicy {
    xml_signatures: XmlSignatureProfile::StrictRsaSha2,
    ..IdpValidationPolicy::recommended()
};
```

The raw `FlowOptions::strict_xml_signature_profile` flag is replaced by
`FlowOptions::xml_signatures`. Set `XmlSignatureProfile::StrictRsaSha2` where
you set `true`. The default, `AllowProviderSupportedForCompatibility`, is the
old `false`.

`SamlError::AlgorithmUnsupported` now displays `signature algorithm is not
allowed`. Before, it displayed `embedded XML signature algorithm is not
allowed`.

## Stop relying on MD5, RIPEMD-160, and short RSA keys under Recommended

This section applies if you use `SpValidationPolicy::recommended`,
`IdpValidationPolicy::recommended`, or their `Default`, and a peer signs with
MD5, with RIPEMD-160, or with an RSA key shorter than 2048 bits. It also
applies if you select `XmlSignatureProfile::StrictRsaSha2` and a peer's RSA
key is shorter than 2048 bits. See
[weak algorithms and keys](../conformance/xml-security-algorithms.md#weak-algorithms-and-keys).

Recommended now sets `xml_signatures` to the new
`XmlSignatureProfile::ExcludeWeakAlgorithms` on both roles. Before, it used
`AllowProviderSupportedForCompatibility`. Compatibility and the raw API are
unchanged, and SHA-1 still verifies.

- A signature that authenticates the received message, or a detached
  `SigAlg`, that uses RSA-MD5, HMAC-MD5, RSA-RIPEMD160, ECDSA-RIPEMD160,
  HMAC-RIPEMD160, or an MD5 or RIPEMD-160 digest returns
  `SamlError::AlgorithmUnsupported`.
- A signing certificate with an RSA key shorter than 2048 bits is not used to
  verify. When the peer has no other usable key, the message returns
  `SamlError::Crypto`. Otherwise a message signed with the short key fails
  signature verification. `StrictRsaSha2` applies the same key rule.

Only the default build and RustCrypto with `crypto-legacy-algorithms` verified
these before, and for RSA only keys of 1024 bits or more. AWS-LC, FIPS, and RustCrypto without that feature already
rejected them. On those builds a detached MD5 or RIPEMD-160 `SigAlg` now
returns `SamlError::AlgorithmUnsupported` instead of the provider's
`SamlError::Crypto`. Ask the peer to sign with RSA-SHA256 and a 2048-bit key or
larger. Until it does, relax that one field:

```rust
use saml_rs::{SpValidationPolicy, XmlSignatureProfile};

let validation = SpValidationPolicy {
    xml_signatures: XmlSignatureProfile::AllowProviderSupportedForCompatibility,
    ..SpValidationPolicy::recommended()
};
```

`XmlSignatureProfile` has a new variant. An exhaustive `match` on it needs an
`ExcludeWeakAlgorithms` arm.

## Remove the software RSA key-transport opt-in

This section applies if you call
`XmlEncryptionPolicy::allow_insecure_software_rsa_key_transport_decryption` or
`XmlEncryptionPolicy::with_insecure_software_rsa_key_transport_decryption_allowed`,
or set `allow_insecure_software_rsa_key_transport_decryption` on
`EntitySetting`, `FlowOptions`, or `AssertionDecryptionOptions`. It also
applies if you configure a decryption key on `crypto-rustcrypto` without that
opt-in: decryption now runs by default.

These items are removed. Delete the call or the assignment. Replace the
`XmlEncryptionPolicy::allow_insecure_software_rsa_key_transport_decryption()`
constructor with `XmlEncryptionPolicy::default()`, or with the constructor of
the policy you want:

```rust
use saml_rs::{XmlEncryptionPolicy, XmlPolicy};

let xml = XmlPolicy {
    encryption: XmlEncryptionPolicy::encrypt_assertions(),
    ..XmlPolicy::default()
};
```

On `crypto-rustcrypto`, RSA key transport runs in `kryptering` on `rsa` 0.10,
which RustSec lists as patched for RUSTSEC-2023-0071. With a decryption key
configured, an encrypted assertion, `<EncryptedID>`, `<EncryptedAttribute>`,
`<NewEncryptedID>`, or the `<EncryptedID>` of a `LogoutRequest` or
`AuthnRequest` now decrypts with the default options, as it already did on
`crypto-aws-lc`. Before, it returned `SamlError::Unsupported`, and a
`ManageNameIDRequest` was refused with `NameIdManagementRefusal::UndecryptableIdentifier`
or `UndecryptableNewIdentifier`. If you relied on that refusal, configure no
decryption key for the entity.

RSA-v1.5 key transport still needs
`XmlEncryptionPolicy::with_rsa15_key_transport_decryption_allowed` and
`crypto-legacy-algorithms`. It no longer needs the removed opt-in.

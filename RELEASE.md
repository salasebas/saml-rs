# How to release saml-rs

Publish `saml-rs` and its maintained aliases, `opensaml` and `samlet`, at
the same version. The group also includes the deprecated `samlify` alias for
its final migration release. All four crates share the root `CHANGELOG.md`.
Only `saml-rs` gets a Git tag (`vX.Y.Z`) and a GitHub release.

## How to publish through release-plz

1. Merge changes to `main` using Conventional Commit titles: `fix: ...`,
   `feat: ...`, or `feat!: ...` / `BREAKING CHANGE: ...`.
2. The `Release-plz` workflow opens or updates a release PR.
3. Check that every grouped crate has the same new version and that each alias
   depends on that version of `saml-rs`. Review `Cargo.lock` and `CHANGELOG.md`.
4. Merge the release PR after CI passes.
5. `release-plz release` publishes the grouped crates, creates the `vX.Y.Z` tag, and
   creates the GitHub release.

`release-plz.toml` sets `release_always = false`, so publication happens only
from the merged release PR, not from every push to `main`.

## Verify the final samlify release

Before retiring `samlify` from the release group, check its
[crates.io page](https://crates.io/crates/samlify). Confirm that the published
version matches the migration release and that its README directs users to
`saml-rs`. Keep that version available for existing users. Reserve yanks for
bad releases, security issues, or legal reasons.

## How to configure GitHub and crates.io

Recommended setup is crates.io trusted publishing:

1. In GitHub, allow Actions to create pull requests.
2. In GitHub, create the `release` environment and allow deployments from the
   `main` branch. The workflow runs from `main`; the `vX.Y.Z` tag is created
   later by release-plz.
3. On crates.io, configure trusted publishing for each crate in the release
   group, including `samlify` for its final release. Use the repository
   `salasebas/saml-rs`, workflow `.github/workflows/release-plz.yml`, and
   environment `release` for each crate.
4. Do not configure `CARGO_REGISTRY_TOKEN` when using trusted publishing.

## How to publish by hand

1. Use the release PR's version in the root package manifest and each grouped
   alias manifest under `crates/`. Check that each alias depends on that
   version of `saml-rs`.
2. Refresh `Cargo.lock` with `cargo build`.
3. Run checks:

   ```bash
   cargo fmt --all --check
   cargo clippy -p saml-rs --all-targets -- -D warnings
   cargo nextest run -p saml-rs
   cargo test -p saml-rs --doc
   cargo check -p saml-rs --no-default-features
   ```

4. Review the root `CHANGELOG.md` generated by release-plz.
5. Publish `saml-rs` first. Once that version is available on crates.io,
   publish the maintained aliases.

   ```bash
   cargo publish -p saml-rs
   cargo publish -p opensaml
   cargo publish -p samlet
   ```

6. For the final migration release, also run `cargo publish -p samlify`
   and verify its crates.io page as described above.
7. Create the `vX.Y.Z` tag and GitHub release for `saml-rs`.

Use `cargo publish -p saml-rs --dry-run` to validate a publish without
uploading.
